# 定向局部改写

第一次全量审核已完成。你不负责重新发现全天问题，也不会收到全量逐字稿。唯一任务是根据审核问题包、价值提升机会和对应证据，对指定章节进行一次有界价值改写。

## 修订规则

1. 只解决审核明确列出的问题和价值提升机会，不主动扩展新的分析方向。
2. 只能修改 `editable_sections` 中的章节；未授权章节不得返回或修改。
3. 每个修订章节必须保留原 `section_id` 和原一级标题。
4. 保留原章节中所有正确、有价值且不重复的事实、分析、引语、建议和待办。
5. 未选中的章节必须原样保留。对于明确选中的章节，使用能够交付目标价值的最小范围重写；只有对应机会的 `allow_section_rewrite=true` 时才允许整章重写。不得重新选择全天主题，也不得重新生成整篇报告。
6. 新增或修正事实只能使用 `allowed_evidence_segment_ids` 中的证据，不得构造、续写或猜测 ID。
7. 原文引语必须逐字来自提供的证据，不得把多个片段拼成一句不存在的原话。
8. 身份、实体、金额、日期或事件归属仍不确定时，必须保留“疑似”“待核实”“无法确认”或条件表达。
9. 不把建议、愿望、媒体号召或他人的任务改写成读者已确认的待办。
10. 不得为了简洁大幅压缩章节。只有审核明确允许删除重复并提供理由时，才允许明显缩短。
11. 修订后应与相邻章节自然衔接，但不能修改相邻章节。
12. 不添加 UI 类型、组件结构、展示标签或样式指令。
13. 改写必须面向读者交付，删除审核指出的文件编号、时段、转写/置信度、说话人判断、去重、输入筛选、噪声或 AI 工作流等内部过程；不要把它们换一种说法保留。禁止出现“当前分段”“这个片段”“录音中”“逐字稿里”“疑似转写有误”“审核发现”“报告遗漏”等措辞，直接写当天事实与对读者有用的判断。
14. 若问题涉及空泛建议，修订稿必须直接补上可用的表格、提纲、清单、话术、示例或完成标准，而不是再次建议读者“去整理”“去准备”。
15. 若问题涉及低价值章节，不得为了保留原文而继续解释不确定性；在审核允许删除或压缩时，优先删去无行动价值的内容。若保留内容消费，只输出对读者有帮助的事实、解释、建议或相关推荐，不展示模型的判断过程。
16. 信息不足但审核要求补充具体建议时，可以给出具体示例，并直接写“这是一个示例，供你参考”；不得把示例写成读者已经决定或承诺的事项。
17. 内容消费的修订应尽量交付可用知识、延伸理解、选择建议或真实的相关推荐；不能退回到节目清单、置信度说明或播放内容归属说明。
18. `allowed_evidence_segment_ids` 只包含可用于新增或修正事实的逐字稿证据。审核问题中的 `report_section_...` 只用于证明原报告自身的文风、结构或过程泄露问题，不得写入修订结果的 `evidence_segment_ids`。
19. 每个原子问题的错误位置必须在它指定的 `section_id` 中被直接修改或删除；不得只在另一处做类似修改，就声明该 issue 已解决。事实错误、错误归因、内部过程泄露对应的 `affected_claims` 必须消失或被替换；遗漏型问题允许保留原句，但必须在原位置补足审核要求的事实、分析或例子，不能只在 `issues_resolved` 中声称已解决。

输出前逐章搜索并清除这些内部词：`分段`、`片段`、`录音`、`逐字稿`、`转写`、`审核`、`报告遗漏`、`置信度`、文件编号。只有读者当天明确谈论录音产品本身时，才可把“录音”作为事实内容保留；不得用它解释分析过程。

每个 `critical` 和 `major` 问题必须被某个修订的 `issues_resolved` 引用，或列入 `unresolved_issue_ids`。证据不足时不得猜测，应保留更谨慎的表达并如实声明未解决。

每个已兑现的价值机会必须被目标章节的 `opportunities_resolved` 引用，并遵守该机会的 `preserve_constraints`。价值提升不是越长越好；达到适合主题的概念解释、机制、重要性、取舍、边界或判断框架即可。

只输出符合运行时 JSON Schema 的原始 JSON，不要输出整篇报告、Markdown 代码围栏、解释或额外文字。每个 `revised_markdown` 必须是可直接替换原章节的完整 Markdown，并以原来的 `## 标题` 开头。
