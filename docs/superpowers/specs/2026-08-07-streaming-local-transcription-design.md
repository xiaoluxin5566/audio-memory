# 本地长音频流式转写设计

## 目标

修复长音频必须等待完整 VAD 和全部音频切片生成后 Whisper 才启动的问题。保持 `mlx-community/whisper-large-v3-turbo`、句段级时间戳、说话人识别、0.5 秒语音边界补偿和现有风险门不变，让不同窗口的 VAD、切片、说话人识别与 Whisper 在时间轴上重叠运行，并让用户在首批结果产出后看到真实进度。

## 已确认问题

当前 `MLXWhisperEngine.transcribe_file` 先调用 VAD 返回完整区间列表，再调用 `_extract_speech_intervals` 顺序生成全部 WAV，最后才遍历切片执行说话人识别和 Whisper。测试音频时长约 3 小时 37 分钟，VAD 产生 1,859 个原始区间，0.5 秒 padding 合并后形成 687 个处理窗口；在全部窗口切完前数据库没有 `Transcript`，因此页面长期显示 0%。

## 架构

采用单文件、有界、顺序提交的生产者—消费者流水线。流水线包含三个职责清晰的单元：

1. VAD 子进程按原始时间顺序发送已完成的语音区间。主进程只保留尚不能确认右边界的最后一个区间；当后续区间证明 gap 大于 1 秒时，对前一区间应用前后各 0.5 秒 padding、完成合并并立即产出。连续语音达到5分钟时强制产出并保留30秒重叠；EOF 时刷新最后一个区间。
2. 窗口准备器从有界队列读取确定边界的窗口，使用 ffmpeg 提取临时 WAV，并完成该窗口的说话人识别。准备完成的窗口写入第二个有界队列。
3. Whisper 消费者按窗口序号读取准备结果，使用 `word_timestamps=False` 转写，并沿用现有边界去重、时间映射、ETA、风险门和数据库提交逻辑。

每个队列容量固定为 2。容量满时上游等待，形成背压，防止3小时以上音频把数百个 PCM 文件或窗口对象同时留在内存和磁盘。单文件内部正常路径保持一个 Whisper worker。窗口超时后终止卡住的进程并创建恢复 worker；仅当现有 `单窗口稳态内存 + max(4 GiB, 实测第二窗口增量) < 物理内存 × 85%` 准入公式成立时，才临时创建一个追赶 worker处理后续最多2个窗口。准入失败时不启动第二进程，恢复 worker先补齐缺失窗口。本次不扩展正常路径的双 Whisper 并行。

## VAD 增量接口

`VoiceActivityDetector.detect()` 不再返回全量列表。每次尝试均在独立子进程中逐帧读取 ffmpeg PCM，并通过 IPC 顺序发送以下事件：

```text
VadIntervalEvent(start_ms, end_ms)
VadProgressEvent(scanned_ms)
VadCompletedEvent(duration_ms, energy_intervals)
VadFailedEvent(error_code)
```

`VadIntervalEvent` 在 sherpa-onnx 的 `vad.front` 可弹出时立即发送，不得先追加到子进程列表等待 EOF。`VadProgressEvent` 最多每秒发送一次，避免 IPC 消息泛滥。主进程增量保存原始 VAD 区间；收到 `VadCompletedEvent` 后完成最终持久化并刷新尾部窗口。失败与完成事件互斥，IPC 关闭但没有终止事件视为预处理失败。

Silero VAD 的 `max_speech_duration` 固定为 `WHISPER_CHUNK_SECONDS = 300` 秒。连续语音达到5分钟时，由VAD正式结束并输出一个真实区间；该区间原样进入 `vad_speech_json`。系统不得为了Whisper分窗向原始VAD证据写入虚拟边界或其他处理标记。

## 窗口边界

- VAD 原始区间仍完整持久化到 `vad_speech_json`，风险门只读取这些原始区间。
- 对 Whisper 输入应用 `DEFAULT_SPEECH_PADDING_MS = 500`，相邻扩展区间重叠或接触时合并。
- 连续语音达到 `WHISPER_CHUNK_SECONDS = 300` 秒时强制关闭当前窗口，相邻强制窗口保留30秒重叠；因此任何窗口不必为了等待后续 gap 或 EOF 而积压超过5分钟原始音频。
- 短 gap 只影响 Whisper 处理窗口合并，不改变原始 VAD 证据。
- VAD相邻真实区间的并集供风险门判断语音支持；30秒重叠仅记录在处理窗口和 `speech_mapping_json`，不得进入 `vad_speech_json`。
- 所有转写时间戳继续映射到原文件时间轴，不使用压缩音频时间轴持久化。

## 顺序、超时与自动追赶

窗口以单调递增的 `window_index` 标识。正常路径的 Whisper 消费和数据库写入按 `window_index` 顺序发生。相邻窗口的30秒重叠继续使用现有 ownership window 和文本签名机制去重；文本签名不得承担断点续传职责。本次不修改风险门状态枚举或卡片分析逻辑。

单窗口 Whisper 推理超时使用 `max(120秒, 本任务稳定窗口耗时 P95 × 3, 窗口音频时长 × 0.5)`；其中0.5为安全 RTF，尚无稳定样本时仍可由另外两项确定硬上限。超时后采用有限越过和自动追赶：

1. 终止卡住的 Whisper 子进程，将超时窗口标记为 `RETRY_PENDING`，并创建恢复 worker优先补转该窗口。
2. 资源准入成立时临时创建一个追赶 worker，允许后续最多2个窗口提前转写；结果进入内存中的有界待提交区，不写数据库、不进入风险门和下游分析。资源准入不成立时不越过，后续窗口继续受背压等待。
3. 缺失窗口补转成功后终止临时追赶模式，只保留一个正常 worker，并按 `window_index` 连续释放待提交结果。
4. 同一窗口最多自动尝试3次。三次均失败时，任务进入 `interrupted/transcription_window_failed`，保留此前检查点；不得永久跳过窗口或向用户交付不完整逐字稿。
5. 待提交区满时停止派发后续窗口，背压继续生效，内存不会随缺失窗口后的结果数量增长。

每个窗口只能处于以下一个状态，状态转换由单一提交协调器串行执行：

```text
READY → RUNNING → COMPLETED_WAITING → COMMITTABLE → COMMITTED
                  ↘ RETRY_PENDING → RETRY_RUNNING → COMMITTABLE
                                      ↘ RETRY_PENDING（未满3次）
                                      ↘ FAILED（达到3次）
```

追赶worker的成功结果只能进入 `COMPLETED_WAITING`。只有从 `last_committed_window_index + 1` 开始形成连续的成功窗口序列，协调器才能将其转为 `COMMITTABLE` 并按序提交。未在上图声明的状态转换一律拒绝并记录受限诊断，不尝试自动纠正。

每个 `job_files` 记录 `last_committed_window_index` 与 `last_committed_source_ms`。一个窗口的全部 Transcript、窗口状态和这两个检查点必须在同一数据库事务中提交。取消或崩溃发生在窗口处理中时，不留下半窗口结果；重新尝试从 `last_committed_window_index + 1` 恢复，并校验原始时间戳。窗口参数或源文件校验发生变化时拒绝使用旧检查点。

## 进度与用户界面

后端继续以已持久化转写片段的最大原始结束时间计算主要转写进度。首批结果前使用真实流水线状态：VAD 已扫描原始音频时长线性映射到0%至3%，首个窗口准备完成记为至少4%，Whisper 真正启动记为至少5%。首条 Transcript 产生后切回基于已转写时间轴的进度，所有对外进度取本任务历史最大值，保证单调不回退。禁止根据墙钟时间制造平滑动画或虚假增长。

前端只显示“处理中”、百分比和可用时的预计耗时，不显示 VAD、切片、队列、GPU或处理模式。准备进度是任务级瞬时状态，不写入逐字稿或业务内容。

## 失败、取消与清理

- VAD 仍在独立子进程运行，沿用最多3次尝试和单次8分钟超时。
- VAD 永久失败仍返回 `local_preprocessing_failed`，不静默回退到全音频慢速路径。
- 用户取消、应用退出或任一流水线单元抛错时，首先设置共享停止信号，然后终止 VAD 与 Whisper 子进程、取消所有队列任务、等待 ffmpeg 子进程退出，并删除本任务已生成的临时 WAV。
- 下游失败后不得继续让生产者写入队列；生产者失败后消费者收到显式结束或错误哨兵，不能永久等待。
- Whisper 完成且该窗口事务提交后立即异步删除对应临时 WAV；失败、取消和应用退出时兜底清理所有在途文件。WAV 为一次性数据，不引入无复用收益的 LRU 缓存。
- 重新尝试复用原始上传文件并从文件级窗口检查点恢复，不依赖文本签名或最大 segment index 推断恢复位置。

## 性能与资源目标

第一轮验收固定使用当前测试机、接通电源、无其他 ML 任务，以及208 MB、时长约3小时37分钟的基准音频。修改前基线固定为流式代码修改前的生产提交、相同模型、padding、说话人识别与风险门配置；冷启动单独记录，稳定路径连续运行至少3次并使用中位数。基线和候选版本均记录代码提交、音频内容哈希、首条延迟、总耗时、Whisper RTF、说话人识别耗时、峰值内存和临时磁盘峰值，不记录音频路径或文本。指标如下：

- 页面首次显示非0进度不超过10秒。
- 首条 Transcript 延迟不超过60秒；完成三次稳定实测后再评估是否收紧至30秒。
- 总耗时中位数降低至少10%即达到优化目标；相对基线变化位于-5%至+5%可在第一轮通过；变慢超过5%视为性能回退，不得通过。
- 总内存不得达到物理内存的85%；无法可靠采样时采用保守限流。
- 任意时刻临时 WAV 不超过4个，包括准备中、待消费、转写中和自动追赶中的文件。
- 用户取消后5秒内任务回到可操作状态，且无 VAD、ffmpeg 或 Whisper 孤儿与僵尸进程。
- 不得因超时、背压或自动追赶静默遗漏任何窗口。

窗口级诊断记录 ffmpeg切片、说话人识别、队列等待和 Whisper 耗时，以及受限的CPU、内存峰值；不得记录音频路径、文本或其他业务内容。窗口准备器与Whisper消费者是并发任务：窗口N由Whisper处理时，窗口N+1可以执行说话人识别，窗口N+2可以进行VAD或切片。实测资源竞争导致Whisper吞吐下降时，通过背压暂停准备器，不关闭说话人识别。

## 测试与验收

自动化测试必须覆盖：

1. 使用可控的慢 VAD 生产者时，第一批 Whisper 调用发生在 VAD 发送 EOF 之前。
2. 第一批 Whisper 调用发生在全部窗口 WAV 生成之前。
3. 队列容量为2；消费者变慢时生产者被背压，待处理窗口数量不无界增长。
4. 单窗口超时会终止并重建 Whisper 子进程；缺失窗口进入 `RETRY_PENDING`，允许后续最多2个结果等待，补转成功后严格按原始顺序释放。
5. 同一窗口三次失败后任务中断且不提交后续结果；重新尝试从最后原子提交的文件级窗口检查点恢复。
6. 状态机中的每条合法转换均可执行，所有未声明转换均被拒绝；覆盖追赶先完成、恢复先完成、第二次重试成功、第三次失败、待提交区满、取消双worker和内存准入失败等交叉时序。
7. 跨窗口结果严格按原始时间排序，30秒重叠不产生重复 Transcript。
8. 0.5秒 padding 合并、超过1秒 gap 保留、EOF 刷新最后区间和5分钟VAD真实分段行为正确；`vad_speech_json`不含30秒处理重叠或虚拟边界。
9. 取消 VAD、ffmpeg、说话人识别和 Whisper 各阶段时任务均能结束，且进程检查无孤儿或僵尸进程。
10. VAD 三次失败仍不启动 Whisper，并保持原有重试和诊断报告行为。
11. 准备阶段进度位于0%到5%，由真实事件驱动且单调递增；首批转写结果出现后整体进度不回退。
12. 临时 WAV 在对应窗口成功提交后立即删除，在途文件数不超过4。
13. 真实208 MB基准音频按同一条件运行三次；总耗时变慢不超过5%，并满足其余性能与资源硬门槛，且首批 Whisper 与后续VAD或窗口准备在时间轴上重叠运行。

## 非目标

- 不修改 Whisper 模型、语言策略或句段级时间戳配置。
- 不关闭说话人识别，不改变风险门阈值和精转写策略。
- 不在本次增加多文件并行、双 Whisper worker 或新的用户设置。
- 不展示已过滤文本或任何技术处理模式。
- 不删除、迁移或重新生成现有业务数据与 Prompt。
