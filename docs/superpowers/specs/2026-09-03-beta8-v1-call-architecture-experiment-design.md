# Beta 8 V1 调用架构 A/B 实验设计

**日期：** 2026-09-03
**状态：** 已获用户授权设计并运行
**上游质量规格：** `docs/superpowers/specs/2026-09-03-beta8-unified-v1-report-quality-design.md`

## 1. 待决策问题

在同一份真实长录音逐字稿、同一 DeepSeek V4 Pro 模型、同一采样参数和同一报告质量契约下，对比：

- **A：一次统一生成**：一次调用同时完成工作沟通边界、场景归属、价值准入、去重和七场景完整 V1 写作。
- **B：两次规划与写作**：第一次只输出薄写作地图，第二次在获得完整逐字稿和写作地图后统一生成七场景完整 V1。

实验不预设 B 更好。A 如果通过所有硬门槛，且人工质量不劣于 B，应选择 A，因为它更简单、更快、更便宜，且没有规划误差传递。

## 2. 实验范围

### 2.1 包含

- 两种架构的原始 V1 生成；
- 严格 JSON/Schema 校验；
- Markdown 格式、结构和冗余编号确定性检查；
- 调用、耗时、Token、输入输出字节数、结束原因和格式修复记录；
- 不含架构标识的盲评产物；
- 两组结果的并排 HTML 页面。

### 2.2 不包含

- Kimi 搜索；
- 初审、全局编辑审核、定向修订和终审；
- 对任一生产 Runner 的修改；
- 对历史报告、数据库或开发环境的发布；
- 根据架构标识调整人工评分。

先比较原始 V1，避免搜索和后续修订遮蔽生成架构本身的差异。

## 3. 公平性约束

1. 两组使用同一份逐字稿字节和 SHA-256。
2. 两组使用同一报告模型 `deepseek-v4-pro`。
3. 两组写作调用使用相同温度、思考参数、超时和最大输出预算。
4. 两组写作使用逐字相同的全局报告质量规则和场景规则。
5. B 的第二次调用额外获得第一次的写作地图；A 不获得隐式或人工生成的地图。
6. 两组均不使用搜索结果、历史卡片、用户画像或上一次评审结论。
7. 架构标识只保存在内部 manifest，盲评页使用由秘密种子生成的 X/Y 顺序。

## 4. 共享输出契约

两组最终 V1 必须返回同一 Schema：

```json
{
  "input_complete": true,
  "input_error": null,
  "scene_results": [
    {
      "scene_id": "work_communication",
      "cards": [
        {
          "card_basis": {
            "type": "work_communication",
            "unit_key": "communication-1",
            "communication_kind": "meeting"
          },
          "markdown": "# 标题\n\n核心信息区\n\n## 章节\n\n完整正文",
          "source_segment_ids": ["seg_0_1"],
          "search_candidates": []
        }
      ],
      "todo_candidates": [],
      "skip_reason": null
    }
  ]
}
```

实验 Schema 必须验证恰好七个场景、真实 segment ID、工作沟通 `unit_key` 唯一、跳过语义、Markdown 标题和核心信息区。

## 5. A/B Prompt 差异

### 5.1 A：一次统一生成

Prompt 同时包含：

- 工作沟通边界；
- 其他六场景价值准入；
- 主体、对象和表达用途；
- 跨场景归属和去重；
- 丰富度、结构、帮助和表达契约；
- 搜索候选和待办候选的现有场景规则。

不要求模型输出思考过程或中间写作地图。

### 5.2 B1：全局内容规划

B1 只输出：

- 工作沟通单元与边界；
- 六场景高价值候选；
- 表达主体、对象和用途；
- 每张卡的价值、必须覆盖的信息与证据 ID；
- 跨场景归属和去重要求。

B1 不输出用户可见 Markdown，不生成搜索和待办候选。

### 5.3 B2：统一 V1 写作

B2 获得完整逐字稿和 B1 地图，使用与 A 相同的写作、场景、搜索候选和待办候选规则，输出与 A 相同的 V1 Schema。

B1 只是辅助，不得限制 B2 对完整逐字稿的访问。B2 如发现 B1 与逐字稿冲突，必须以逐字稿为准，并通过内部 `plan_corrections` 字段记录修正；`plan_corrections` 不显示给用户，不参与卡片内容评分。

## 6. 评价维度

### 6.1 硬门槛

任一架构出现以下情况即不能直接入选：

- 输出截断或最终 JSON 无法恢复；
- 缺失场景、重复场景或引用未知 segment ID；
- 把第三方案例、他人状态或媒体内容写成用户本人事实；
- 同一次工作沟通被拆成多张卡；
- 不同工作沟通被错误合并；
- 明显高价值内容整体遗漏；
- 搜索来源错配不在本实验中检查，因为实验不执行搜索。

### 6.2 质量指标

在硬门槛之后比较：

- 工作沟通边界准确度；
- 高价值内容覆盖；
- 低价值卡比例；
- 跨卡和跨场景重复；
- 主体与观点归属；
- 卡片信息丰富度；
- 核心信息的首屏可见性；
- 结构化呈现与内容的匹配度；
- 建议的具体性、可执行性和场景适配度；
- 是否直接与用户交流，避免报告腔和材料复述腔；
- 人工总体偏好。

### 6.3 效率指标

- 提供商模型响应次数；
- 格式修复次数；
- 输入、输出和合计 Token；
- 模型耗时与墙钟时间；
- 可计量费用；
- 输出卡数和 Markdown 字符数。

## 7. 评价方法

### 7.1 确定性检查

程序直接检查 Schema、segment ID、场景集合、标题、手工编号、段落与章节结构、表格数量、卡数、字符数、调用和 Token。这些检查不代替语义评价。

### 7.2 语义评价

对 X/Y 产物分别运行同一份审核标准，输出具体问题、严重性和证据，不允许审核器知道 X/Y 对应哪种架构。语义审核是辅助证据，不以一个总分覆盖具体硬门槛。

### 7.3 人工盲评

产出一个本地并排页，只显示“方案 X”与“方案 Y”，不显示架构、调用次数、成本或提示词。用户按实际阅读体验选择：

- X 明显更好；
- Y 明显更好；
- 接近，无显著差异。

并记录具体原因，不只记一个分数。

## 8. 选型规则

1. 任一方未通过硬门槛，不能直接入选。
2. 只有一方通过所有硬门槛时，选择通过者。
3. 两方都通过时，如人工明确偏好一方，选择该方。
4. 两方质量接近且无明显偏好时，选择 A（一次统一生成）。
5. B 只有在减少了具体错误、增加了重要内容或明显提升阅读体验时才能凭借质量收益抵消额外的调用、时间和成本。
6. 用户盲评是最终产品体验证据；在用户未完成盲评前，可以得出“某方未通过硬门槛”，但不将两方都达标时的主观优劣宣布为最终产品决策。

## 9. 产物

每次实验生成独立目录，至少包含：

```text
input-summary.json
experiment-manifest.json
variant-a/
  raw-response.txt
  result.json
  cards/
  metrics.json
variant-b/
  plan-raw-response.txt
  plan.json
  raw-response.txt
  result.json
  cards/
  metrics.json
deterministic-review.json
semantic-review.json
blind-map.json
comparison.html
decision-summary.md
```

`experiment-manifest.json` 保存模型、参数、Prompt 哈希、Schema 哈希、输入哈希和起止时间。`blind-map.json` 只用于实验结束后解盲，并排页不读取该文件。

## 10. 付费与状态边界

- 本实验使用真实 DeepSeek V4 Pro，属于付费调用；用户已明确同意运行本 A/B 实验。
- 实验脚本必须仍要求显式的命令行确认口令，避免被无意执行。
- 本实验不调用 Kimi，不发布卡片，不写入开发或生产数据库。
- 输出只写入新建的评测目录，不覆盖已有评测产物。
