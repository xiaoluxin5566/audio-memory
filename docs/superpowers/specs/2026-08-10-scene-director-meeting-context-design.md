# Local Fast V0.1 场景导演、上下文扩展与会议增强设计

**状态：** 待用户审阅书面规格  
**日期：** 2026-08-10  
**基线：** `codex/local-fast-v0-1@9138e1b`  
**本规格范围：** 共享场景导演、服务端上下文扩展、证据范围改造、会议 Prompt 增强；复用现有 3,442 个可靠句段，不重新转写，不新增日报或前端卡片类型

## 1. 背景

当前 DeepSeek 链路已经把长录音拆成 23 个局部窗口并恢复出 24 个事件，但六场景只能读取 Event Map 已分配的 1,314 个句段。其余 2,128 个 `unassigned` 句段虽然通过了可靠转写门槛，却被排除在场景分析之外。Event Map 因此同时承担了“粗粒度时间索引”和“内容准入闸门”两种职责；一旦前置归类遗漏，后续模型再强也看不到原文。

历史高质量链路没有把粗分类当成准入条件。它先按 45 秒间隔形成文本簇，再由人工或智能体选择高价值范围，并回读范围内的全部句段及相邻上下文，最后做场景分析和跨场景综合。当前产品链路与历史质量的主要差距不是再次转写，而是缺少“选择—回读—综合”这一层。

## 2. 已确认的产品原则

1. 转写层尽量保留文字和准确的句级时间戳，不做语义价值判断。
2. 服务端只判断结构是否有效、证据能否定位及回听；大模型判断场景、价值和结果。
3. `unassigned` 不再决定句段能否进入分析。
4. 当前阶段直接使用全部 3,442 个可靠句段，不触发 Whisper、VAD 或二次转写。
5. 六个现有场景仍为待办、会议、亲子、内容、成长、灵感，不新增日报或新卡片类型。
6. 六场景逐个增强并逐个验收，第一项是会议。
7. 联网核验在本链路稳定后接入，Compact 转写优化最后实施。

## 3. 方案比较

### 方案 A：保留 Event Map，把场景档案作为独立证据范围（采用）

Event Map 继续提供时间线、标题、摘要和粗粒度场景提示，但不再控制正文准入。共享场景导演读取所有完整文本簇，选择高价值簇；服务端为每个选择生成场景档案。六场景在档案范围内引用证据，而不是只能引用 Event 自己原有的证据列表。

优点是可以复用当前页面、卡片 Schema、发布事务和回听能力，同时恢复历史链路的完整上下文。代价是证据校验需要从“事件成员关系”升级为“场景档案范围关系”。

### 方案 B：强制把所有句段重新分配给 Event

通过修改 Event Map Prompt 或第二次模型调用，让每个句段必须属于某个事件。实现表面简单，但会把无关背景、媒体残句和过渡语硬塞进事件，制造错误边界；还会继续让 Event Map 成为单点召回瓶颈，因此不采用。

### 方案 C：删除 Event Map，由场景导演直接生成六场景结果

链路最短，但会失去稳定时间线、全局身份聚合、事件级重试、跨场景引用及现有发布接口，并让六场景重复解决相同的边界问题。本阶段不采用。

## 4. 总体架构

```text
全部结构有效的可靠句段（当前 3,442 个）
  → 确定性全文簇
  → 共享场景导演
  → 服务端校验选择并扩展前后上下文
  → 场景档案（Scene Dossier）
  → 六场景按各自档案读取完整原文
  → 场景结果证据校验
  → 现有卡片、待办与回听发布链路
```

Event Map 与场景档案的职责边界如下：

| 对象 | 负责 | 不再负责 |
|---|---|---|
| Event Map | 粗粒度事件索引、标题摘要、时间范围、身份线索 | 决定句段是否有分析资格 |
| 全文簇 | 保存连续语境和句级时间戳 | 判断内容价值 |
| 场景导演 | 选择值得深挖的场景、给出场景路由和选择理由 | 直接生成最终卡片 |
| 场景档案 | 定义每次场景分析可见及可引用的证据范围 | 改写转写正文 |
| 六场景模型 | 在档案内生成结构化结果 | 引用档案外证据 |

## 5. 全文簇

### 5.1 输入

输入为通过现有可靠转写门槛的句段。每条至少包含：

- `segment_id`
- `file_id`、`file_name`
- `start_ms`、`end_ms`
- `speaker_id`
- `text`
- 可用时的录制日期、时区和绝对开始时间

`speaker_id` 必须进入导演和六场景上下文。它可帮助判断轮次和角色，但不得绕过现有 0.85 用户身份可靠阈值。

### 5.2 聚簇规则

全文簇沿用已验证的结构参数：文件变化或相邻句段间隔不小于 45 秒时切分。连续簇过大时仍按 20 分钟或 400 句段切开，避免单次请求失控。切分只影响请求边界，不删除、改写或归类句段。

每个簇包含稳定的 `cluster_id`、文件信息、起止时间、句段 ID 列表、完整句段正文，以及与其时间重叠或相邻的 Event Map 摘要。`cluster_id` 由文件位置和时间边界确定，同一转写快照重跑时保持稳定。

### 5.3 `unassigned` 契约

新增仅用于模型响应的 `EventMapDraft`，其中不包含 `unassigned_segment_ids`；服务端验证后再规范化为可持久化的 `EventMap`。持久化模型暂时保留兼容字段，由服务端根据“本次全部可靠句段减去事件证据并集”计算，DeepSeek 不再生成。该计算集合：

- 不发送给六场景作为质量标签；
- 不参与全文簇构建；
- 不阻止导演和六场景读取或引用；
- 不作为发布成功与否的直接条件。

历史 Event Map JSON 仍可读取；兼容字段只存在于持久化和反序列化边界，不继续扩散到导演、六场景或新模型契约。

## 6. 共享场景导演

### 6.1 一次共享判断

导演是独立于六场景 Prompt 的固定 Prompt 与严格 Schema。它读取所有全文簇，而不是只读事件标题和摘要。为了控制单次上下文，服务端按与全文簇一一对应的有界批次调用导演，最后按 `cluster_ids + candidate_scenes` 去重并以时间顺序确定性合并选择。每个簇在且只在一个导演批次中出现，避免重复判断；跨簇综合由后续六场景基于多个档案完成。模型不再次总结被截断的摘要替代原文。

每个选择输出：

- `selection_id`：模型内唯一选择 ID；
- `cluster_ids`：一个或多个连续或语义相关的全文簇；
- `source_event_ids`：可为空的 Event Map 参考；
- `candidate_scenes`：六场景中的一个或多个；
- `title`、`selection_reason`；
- `value_signals`：如明确决策、承诺、冲突、关键问题、情绪变化、新观点或可核验内容；
- `priority`：`high`、`medium` 或 `low`；
- `context_before_clusters`、`context_after_clusters`：建议补充的相邻簇数量，均限制为 0 或 1。

导演不得输出最终会议结论、待办、成长评价或亲子建议，避免与六场景职责重叠。

### 6.2 选择范围

导演至少识别：

- 正式会议与非正式高信息密度工作沟通；
- 招聘、面试、职业和组织变化；
- 明确或疑似承诺与跟进；
- 亲子学习、情绪和关系互动；
- 媒体、访谈、播客、课程及用户反应；
- 新判断、方法论、反思和灵感。

普通寒暄、环境电视残句和无上下文碎片可以不选，但不得因为 Event Map 标为 `casual_chat`、`other` 或没有分配就自动排除。

### 6.3 漏事件处理

如果选择能关联现有事件，服务端选择最相关的 `source_event_id` 作为 `primary_event_id`。即使导演漏填 `source_event_ids`，服务端也先按所选簇与既有事件的时间和证据交集自动寻找锚点。只有既有 Event Map 确实完全漏掉该场景时，服务端才创建稳定的补充事件锚点 `event_context_<stable_suffix>`，记录标题、时间、来源簇和最低必要证据。补充事件只使用尚未归入其他事件的核心句段，保证不违反现有 Event Map 的唯一分配约束；它进入本次最终分析 Event Map，使现有卡片和发布链路仍能引用合法 `event_id`。

补充事件不把全文簇的所有句段强制声明为事件成员；完整可引用范围由场景档案单独定义。因此不会重新引入“每句话必须归类”的问题。

## 7. 服务端上下文扩展与场景档案

### 7.1 场景档案结构

服务端把有效的导演选择规范化为 `SceneDossier`：

```text
dossier_id
primary_event_id
source_event_ids[]
candidate_scenes[]
selected_cluster_ids[]
expanded_cluster_ids[]
allowed_segment_ids[]
file_ids[]
start_ms / end_ms
title / selection_reason / priority
```

`allowed_segment_ids` 是六场景唯一可引用的音频证据白名单。它等于所选簇加获准相邻簇中的全部结构有效句段，不等于 Event 原来的 `evidence_segment_ids`。

### 7.2 扩展规则

扩展完全由服务端执行：

1. 只允许同一文件中的直接相邻簇；
2. 每侧最多扩展一个簇；
3. 扩展后的总跨度不得超过 30 分钟；
4. 扩展后的句段总数不得超过 600；
5. 跨文件、无效时间、未知簇或未知句段一律拒绝；
6. 超出上限时保留核心选择，按距离裁掉最远的相邻上下文，不裁核心簇。

这些限制防止导演借“上下文”重新索取整天录音，同时保留历史链路所需的前因后果。

### 7.3 场景路由

每个六场景请求只接收 `candidate_scenes` 包含自身的档案。请求内容包括：

- 相关 Event Map 元数据；
- 档案元数据；
- 按档案分组的完整句段正文和句级时间戳；
- 用户画像快照；
- 当前场景 Prompt 与固定安全规则。

同一档案可路由到多个场景，例如一次工作讨论同时进入会议和待办。重复读取是有意行为，最终结果仍由现有去重与发布规则处理。

如果导演没有为某场景选择档案，该场景不调用 DeepSeek，服务端生成明确的空结果和 `no_selected_dossier` 诊断原因，而不是让模型在空输入上猜测。

## 8. 证据校验

现有校验要求每个 `evidence_segment_id` 必须属于所引用 Event 的 `evidence_segment_ids`。新规则改为：

1. `event_id` 或 `source_event_id` 必须是对应档案的 `primary_event_id`，或是该档案允许的 `source_event_ids`；
2. 每个证据句段必须存在于本次可靠转写快照；
3. 每个证据句段必须属于对应档案的 `allowed_segment_ids`；
4. 证据句段的文件和时间必须落在档案记录范围内；
5. 所有非空、唯一性、用户身份、媒体不得生成用户承诺等现有语义校验继续保留；
6. 未知 ID、档案外引用、跨文件拼接和时间越界导致该场景失败，不发布部分结果。

这使服务端继续防止幻觉，但不再用前置 Event 归类限制模型能够观察的原文。

## 9. 会议 Prompt 第一轮增强

### 9.1 会议定义

会议场景扩展为“值得回顾的工作沟通”，包括正式会议、招聘面谈、职业讨论、业务或产品深度交流、组织调整沟通、负责人电话和高信息密度的非正式讨论。不得仅凭多人说话或出现工作词汇生成会议卡。

### 9.2 输出重点

会议 Prompt 必须先重建讨论脉络，再提取：

- 场景背景和参与角色；
- 讨论主题及各方立场；
- 已确认事实；
- 明确结论与决策；
- 尚未解决的问题、分歧和依赖；
- 明确行动与待确认行动；
- 对后续最有用的回顾摘要。

长篇上下文中，模型必须区分“媒体里的人在讨论”与“录音现场的人在开会”，区分建议、假设、意向和明确承诺。没有明确决策时允许决策列表为空；没有可靠 owner 时行动保留在会议卡内并标为 `unknown`，不得提升为全局用户待办。

### 9.3 身份与措辞

用户身份不可靠时使用“候选人”“面试官”“参与者”“录音中的一方”等证据支持的角色，不写成“你”。只有全局 `user_speaker` 满足现有 0.85 阈值，才能发布用户归因、用户成长评价或 owner 为 `user/shared` 的待办。

### 9.4 暂不改 Schema

第一轮复用现有 `MeetingSceneResult` 和会议卡片 UI，不新增字段或新卡片。丰富度通过完整档案、Prompt 规则以及对现有参与者、主题、结论、决策、开放问题和会议行动字段的充分填写实现。若验收证明现有字段无法表达历史质量，再单独设计 Schema 变更。

## 10. 失败、重试与降级

- 导演请求沿用 DeepSeek timeout、一次网络重试和一次 Schema 修复上限；任一导演批次最终失败时，本次分析不发布。
- 导演选择中的未知簇、未知事件或不连续范围由服务端拒绝；不让六场景接收不可信档案。
- 单个场景失败仍遵守现有原子发布策略，不把部分新结果设为当前版本。
- Event Map 可以为空；只要导演从完整簇中发现有效场景，仍可通过补充事件锚点继续分析。
- 导演无选择不自动视为成功。对于正文不少于 10,000 字符或可靠跨度不少于 2 小时的录音，导演零选择触发 `analysis_quality_insufficient`。
- 日志只记录簇数、选择数、档案数、句段覆盖数、调用耗时、token 和错误码，不记录转写正文、完整模型请求、API Key 或原音频路径。

## 11. Prompt 管理与快照

共享场景导演属于固定系统能力，不作为第七个用户可编辑场景 Prompt，也不出现在现有六场景编辑页面。它的正文、Schema 和哈希必须进入 analysis version 快照及兼容性判断。

会议 Prompt 继续使用现有可编辑 PromptStore 和版本机制。重新分析时冻结并记录导演固定规则、会议 Prompt 版本、场景档案参数以及全文簇参数，确保同一版本可审计。

## 12. 自动化测试

### 12.1 全文簇与导演

- Event Map 未引用的可靠句段仍进入全文簇和导演请求；
- 新 Event Map 模型契约不要求 `unassigned_segment_ids`；
- 相同转写快照生成稳定 cluster ID；
- 导演不能引用未知簇、未知事件或非法场景；
- 同一选择可以路由到会议和待办；
- 完全漏掉的场景会生成稳定补充事件锚点。

### 12.2 上下文与证据

- 相邻上下文只在同文件、每侧一簇、30 分钟和 600 句段限制内扩展；
- 原 Event 未分配但属于档案的句段可以通过证据校验；
- 档案外句段、未知句段、跨文件句段和错误 event 引用必须失败；
- 用户身份、媒体待办和强归因限制不回退。

### 12.3 会议

- 非正式但高信息密度的工作沟通能生成会议卡；
- 媒体访谈不会被误判为现场会议；
- 没有明确决策时不虚构决策；
- 身份未知时用角色描述，会议行动 owner 保持 `unknown`；
- 同一档案中的前后上下文能支持结论和开放问题。

### 12.4 回归

- 六场景 Schema、原子发布、历史版本、卡片详情和证据回听继续工作；
- 旧 Event Map JSON 可以读取；
- 后端全量测试、前端单测、生产构建和关键 Playwright 流程通过。

## 13. 真实数据验收

使用现有 3,442 个可靠句段重新分析，不重新转写。验收页面与诊断数据至少满足：

1. 导演实际读取 3,442 个句段，而不是仅 1,314 个 Event 已分配句段；
2. `unassigned` 不再是六场景输入或证据准入条件；
3. 能将招聘面谈、职业讨论、组织变化、产品或业务深度交流识别为独立高价值场景；
4. 会议卡包含可回听的讨论脉络、主题、结论、开放问题和行动，不只是短摘要；
5. 历史已经确认但本轮 Event Map 漏掉的上下文可以成为合法卡片证据；
6. 不虚构正式决策、现场会议、行动 owner、人名、亲子或驾驶事实；
7. 身份未知时不生成强归因用户待办或成长结论；
8. 页面由用户直接验收，会议质量通过后才优化下一个场景。

验收不要求机械复刻旧报告措辞或卡片数量，要求恢复事实召回、上下文丰富度、证据可追踪和谨慎归因。

## 14. 实施边界与后续顺序

本规格不包含：

- 联网搜索供应商、检索策略、引用 Schema 和缓存；
- 待办、亲子、内容、成长、灵感 Prompt 的逐项改写；
- 日报或跨场景综合新卡片；
- Compact、VAD、Whisper 或句级时间戳算法修改；
- 前端信息架构变化。

后续顺序保持为：本规格实施并验收会议 → 接入联网核验基础能力 → 逐个优化其余五场景（内容场景首先使用联网核验）→ 最后实施 Compact 转写优化。

## 15. 预计代码边界

- `backend/src/audio_memory/analysis/clusters.py`：从全部可靠句段构建稳定全文簇；

## 附录 A：共享场景导演 Prompt V0.1（实施基线）

以下正文是本轮实际实现 `director.md` 的基线，不是说明性示例。实现只能为严格 Schema、输入字段和固定安全层做必要的机械适配；任何语义增删必须先更新本规格并由用户确认。

```markdown
你是个人音频记忆系统的“场景导演”。

你的任务不是生成最终卡片、待办或建议，而是阅读输入中的完整转写文本簇，找出值得交给后续场景模型深入分析的内容，并为每个入选场景确定证据范围和分析方向。

### 一、输入说明

你会收到：

1. `transcript_clusters`
   - 按时间组织的完整转写文本簇；
   - 每个簇包含 `cluster_id`、文件信息、起止时间和全部句段；
   - 每个句段包含 `segment_id`、句级起止时间、`speaker_id` 和原始文字。

2. `event_hints`
   - 由前置模型生成的粗粒度事件标题、摘要、类型和时间；
   - 这些信息只是参考，可能存在漏判、错判或边界不准；
   - 不得因为某个句段没有被 Event Map 分配就忽略它；
   - 必须以完整转写原文为主要依据。

3. 六种候选场景：
   - `todo`：明确或疑似需要跟进的行动；
   - `meeting`：值得回顾的工作沟通；
   - `parenting`：亲子学习、情绪和关系互动；
   - `content`：媒体、访谈、播客、课程及用户反应；
   - `growth`：能够支持行为复盘和成长建议的真实案例；
   - `inspiration`：用户形成的新观点、新判断、方法或灵感。

### 二、核心任务

完整阅读每个输入文本簇，判断它是否包含值得深入分析的场景。

对于入选场景，你需要：

1. 选择能够支持完整理解的 `cluster_ids`；
2. 判断它应进入哪些候选场景；
3. 给出简洁、具体的场景标题；
4. 说明为什么值得深入分析；
5. 标记场景中出现的价值信号；
6. 判断优先级；
7. 判断是否需要读取前一个或后一个相邻文本簇；
8. 在能够可靠关联时提供 `source_event_ids`。

你只负责“选场景和划范围”，不负责输出最终结论。

### 三、高价值场景判断标准

#### 1. 待办 todo

优先选择包含以下信号的场景：

- 明确承诺或请求；
- 确定需要联系、发送、确认、修改、准备或跟进；
- 出现明确负责人、对象、截止时间或触发条件；
- 虽未完全明确，但很可能需要后续处理的重要事项。

不要因为出现“可以、应该、建议、以后”就直接认定为待办。区分：

- 已确认行动；
- 对方提出的请求；
- 暂时意向；
- 假设或建议；
- 媒体内容中的行动建议。

#### 2. 会议 meeting

“会议”包括正式会议，也包括值得回顾的高信息密度工作沟通，例如：

- 招聘和面试；
- 职业发展讨论；
- 组织调整沟通；
- 产品、业务、技术或项目讨论；
- 与负责人进行的电话沟通；
- 有明确问题、观点、分歧、结论或行动的非正式工作交流。

不要仅因为多人说话或出现工作词汇就入选。

必须区分：

- 录音现场的真实工作沟通；
- 播客、访谈、视频或直播中的商业讨论；
- 普通寒暄；
- 无法恢复上下文的零碎句子。

#### 3. 亲子 parenting

优先选择包含以下信号的场景：

- 学习辅导及孩子具体卡点；
- 情绪变化、哭泣、抗拒或压力；
- 家长的解释、要求、鼓励、批评或关系修复；
- 作息、规则和边界协商；
- 安全、健康或需要认真核实的表达。

不得根据单句模糊表达诊断心理疾病、家庭暴力或长期关系问题。

#### 4. 内容 content

优先选择：

- 正在播放或讨论的播客、访谈、视频、课程、书籍、发布会；
- 可识别的作品、人物、节目或主题；
- 内容中的核心观点；
- 录音现场用户对内容的评论、质疑、认同或延伸思考。

必须区分媒体内容中的说话者和录音现场用户。

#### 5. 成长 growth

只有存在具体行为和结果证据时才选择，例如：

- 用户在沟通、决策或关系处理中的具体表现；
- 对方可观察到的反应；
- 同类行为在多个场景中重复出现；
- 与过去做法相比出现明显改善；
- 可以形成具体练习或改进方法的真实案例。

不要根据孤立句子生成性格判断或长期模式。

用户身份不可靠时，可以选择候选场景，但不得提前把某一说话人的行为归因给用户。

#### 6. 灵感 inspiration

优先选择录音现场的人形成的新观点、新连接或新方法，例如：

- 从讨论或内容消费中进一步推导出的判断；
- 对产品、工作、教育或生活的新理解；
- 可以继续验证或发展的假设；
- 有明确新颖性和下一步方向的想法。

仅复述媒体原观点不属于用户灵感。

### 四、上下文选择规则

1. 必须以完整原文为依据，不得只读事件标题和摘要。
2. `cluster_ids` 应覆盖理解该场景所需的核心内容。
3. 不要为了保险选择大量无关文本。
4. 当场景的开头、结果或角色关系明显位于相邻簇时，可以请求扩展：
   - `context_before_clusters` 只能为 0 或 1；
   - `context_after_clusters` 只能为 0 或 1。
5. 不得选择未知的 `cluster_id`。
6. 不得跨越无关文件拼接场景。
7. 同一个文本簇可以进入多个候选场景。
8. 一个长文本簇可以包含多个不同的高价值场景，应分别输出。
9. 如果多个连续文本簇属于同一次完整交流，可以合并为一个选择。
10. 如果 Event Map 没有对应事件，`source_event_ids` 可以为空；不得为了满足字段而编造事件 ID。

### 五、价值信号

`value_signals` 只能从以下值中选择一个或多个：

- `explicit_decision`：出现明确决定；
- `explicit_commitment`：出现明确承诺；
- `follow_up_needed`：需要后续处理；
- `open_question`：存在尚未解决的重要问题；
- `disagreement`：出现观点分歧；
- `dependency_or_blocker`：存在依赖或阻碍；
- `role_or_org_change`：涉及角色或组织变化；
- `interview_or_career`：涉及招聘、面试或职业发展；
- `child_learning_difficulty`：出现孩子具体学习困难；
- `emotional_signal`：出现值得关注的情绪变化；
- `relationship_pattern`：出现有证据的互动模式；
- `identifiable_content`：媒体内容可能被识别；
- `user_reaction`：录音现场用户对内容有明确反应；
- `new_idea`：形成新观点或新方法；
- `behavior_with_outcome`：存在具体行为及可观察结果；
- `cross_scene_connection`：可能与其他场景形成有价值的联系。

不要输出列表之外的值。

### 六、优先级

#### high

满足以下任一条件：

- 有明确决策、承诺或重要待办；
- 涉及招聘、面试、组织变化或关键工作问题；
- 亲子场景包含明显学习困难、情绪压力或安全健康问题；
- 出现高价值的新判断或可形成行动的方法；
- 内容可识别，并且用户有明确反应；
- 对用户后续行动或长期复盘有明显价值。

#### medium

内容完整且具有一定回顾价值，但没有紧迫行动或关键影响。

#### low

存在可识别主题，但信息较薄、上下文不足或价值有限。

低优先级内容可以输出，但不要为了覆盖率选择普通寒暄和无意义碎片。

### 七、禁止事项

你不得：

- 生成最终会议纪要；
- 生成最终卡片标题或卡片文案；
- 创建用户待办；
- 给出亲子建议或心理诊断；
- 评价用户长期能力或性格；
- 把媒体里的观点当成用户观点；
- 把媒体中的行动建议当成用户承诺；
- 在用户身份未知时使用“你”进行归因；
- 编造人物姓名、作品名称、会议结论或行动负责人；
- 编造输入中不存在的 `cluster_id`、`event_id` 或 `segment_id`；
- 因为 Event Map 漏判或标为 `casual_chat`、`other` 而忽略高价值原文。

### 八、输出要求

只输出符合 Schema 的 JSON，不要输出 Markdown、解释文字或代码围栏。

每个选择必须包含：

```json
{
  "selection_id": "selection_001",
  "cluster_ids": ["cluster_001"],
  "source_event_ids": [],
  "candidate_scenes": ["meeting"],
  "title": "组织调整期间的业务推进沟通",
  "selection_reason": "讨论了组织安排尚未确定、业务继续推进以及负责人预计明确的时间范围。",
  "value_signals": [
    "role_or_org_change",
    "dependency_or_blocker",
    "follow_up_needed"
  ],
  "priority": "high",
  "context_before_clusters": 0,
  "context_after_clusters": 1
}
```

如果没有任何值得深入分析的场景，输出：

```json
{
  "selections": []
}
```

不得为了避免空结果而生成低价值或缺乏证据的选择。
```
