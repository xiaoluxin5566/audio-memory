# Audio Memory 历史音频批量重分析设计

**状态：** 已完成风险修订，待用户复核

## 1. 目标

用户频繁修改六场景 Prompt 后，可以使用当前模型和最新 Prompt 重新处理全部历史上传，而不重新上传音频、不重新执行 Whisper 转写或说话人识别。

该功能只重跑模型相关阶段，不能修改或重复保存原始音频、结构化转写、反馈与追问记录。第一阶段同时建立分析版本能力，为后续 Kimi、DeepSeek、OpenAI 同源转写对比提供基础。

## 2. 核心术语与处理单位

- **原始上传批次（Source Batch）**：用户一次点击「开始分析」提交的一个或多个音频文件，对应一个原始 `job_id`。事件地图、六场景结果和卡片均以此为最小分析单位。
- **分析版本（Analysis Version）**：同一原始上传批次使用某一模型和某一组 Prompt 生成的一套完整结果。
- **历史重分析批次（Reanalysis Batch）**：用户一次点击「重新分析全部历史」后创建的后台任务，包含多个原始上传批次。

历史重分析必须按原始上传批次处理，不得把同一次上传中的多个音频文件拆开分析。界面统一同时显示「上传批次数」和「音频文件数」，避免“历史音频数量”产生歧义。

## 3. 入口与首页状态

- 顶部导航新增「重新分析全部历史」，位于「清除所有历史」左侧。
- 入口在信息流、音频历史和 Prompt 设置三个页面始终可见。
- 没有已完成原始上传批次时按钮禁用。
- 有运行或暂停中的历史重分析批次时，按钮展示 `重新分析中 X/Y` 或 `继续重新分析`，禁止创建第二个并行批次。
- 运行期间用户可以进入任意页面、刷新网页或关闭浏览器，本地后端继续执行。
- 当前打开的旧卡片详情不会因版本切换突然关闭；关闭后重新进入时展示当前版本。

## 4. 预览与确认窗口

点击入口后先获取实时预览，确认窗口必须展示：

- 待处理的原始上传批次数；
- 音频文件总数与转写文字总量；
- 当前模型厂商与模型名称；
- 六场景 Prompt 版本；
- 预计模型调用次数区间；
- 「不会重新转写音频」说明；
- 「会调用当前模型并产生 API 费用，实际费用由厂商决定」提醒；
- 取消与「开始重新分析」按钮。

预计调用次数按每个上传批次六场景调用、可能的事件地图重建和一次 Schema 修复上限计算，只作为范围提示，不承诺实际费用。

当前厂商未配置、不可用、正在校验或处于限流冷却期时，不允许启动；窗口提供进入模型配置的入口。

## 5. 批次快照

用户确认时创建不可变快照，固定：

- 批次内全部已完成原始 `job_id` 及其文件数量；
- 当前厂商、模型 ID、模型配置版本与 `credential_generation`，不保存 API Key；
- 六场景自然语言 Prompt 的完整内容、版本和 SHA-256；
- 系统 Prompt、公共 Prompt、事件地图 Prompt 和 Schema 的版本与 SHA-256；
- 批次开始前的隐藏画像快照；
- 创建时间、任务总数和处理顺序。

只保存版本号不构成有效快照，因为用户可能直接修改本地 Prompt 文件。批次运行期间修改 Prompt 或切换厂商不影响快照；修改当前厂商的 Key 会改变 `credential_generation`，此时批次在当前模型请求结束后暂停。用户确认使用新 Key 继续时，必须清除当前尚未发布原始上传项的模型检查点并从事件地图之后重新执行六场景；已成功发布的历史项不重跑，禁止把两代凭据生成的场景混成一个分析版本。

确认后新增的音频不进入当前历史批次。未完成、失败或被放弃的上传任务不进入批次。

## 6. 分析版本数据模型

原始上传数据与模型生成结果分层保存：

- 原始 `AnalysisJob`、`JobFile`、`Transcript` 和音频文件只有一份；
- 每个原始上传批次拥有多个 `AnalysisVersion`；
- `Batch.current_analysis_version_id` 指向信息流当前发布版本；
- `Card`、模型待办候选和画像候选关联 `analysis_version_id`；
- 每个分析版本记录模型、Prompt、事件地图、状态、错误和来源历史重分析批次；
- 旧分析版本只用于反馈、QA 溯源和未来模型对比，不参与普通信息流查询。

同一原始上传批次的新版本成功后，只在事务中切换 `current_analysis_version_id`，不得物理删除旧版本。新版本沿用原批次的上传时间、自然日和排序位置；单独保存 `reanalyzed_at`，但它不参与首页时间线排序。

## 7. 重分析链路

每个原始上传批次复用：

- 原始音频记录；
- 结构化转写、片段 ID 和词级时间戳；
- 说话人识别结果；
- 录制日期、时区和其他可靠元数据。

事件地图只有同时满足以下条件才复用：

- 已通过 Schema 与证据完整性校验；
- 固定事件地图 Prompt、事件 Schema 和结构化转写版本均与批次快照兼容；
- 事件地图内容哈希有效；
- 所有 `evidence_segment_ids` 仍存在于当前结构化转写。

不满足任一条件时重新生成事件地图，但任何情况下都不重新执行 Whisper 或说话人识别。

单个原始上传批次的模型阶段依次执行：

1. 读取或重建事件地图；
2. 使用批次开始时冻结的画像快照执行六场景分析；
3. 每个场景成功后立即保存检查点；
4. 解析 Schema，修复请求最多一次；
5. 校验证据、事件引用和用户身份门槛；
6. 生成卡片、待办候选与画像候选；
7. 六场景全部成功后创建完整分析版本并切换当前版本。

模型已返回但检查点尚未落盘时进程崩溃，恢复后可能重复一次厂商请求。系统通过逐场景检查点降低概率，但不承诺外部 API 绝对不重复计费。

## 8. 发布与卡片替换

- 新版本六场景全部成功并通过校验后，才在一个数据库事务中发布。
- 发布事务失败时，当前版本指针保持不变，继续展示完整旧结果。
- 新 Prompt 判定某场景不再生成时，新版本发布后该旧场景卡片从当前信息流消失。
- 新版本分析失败时，整个原始上传批次继续展示旧版本，不允许新旧场景混搭。
- 信息流不得出现同一原始上传批次的两套当前卡片，也不得在重分析期间出现空窗。
- 历史重分析默认从最近的原始上传批次向更早批次处理。

## 9. QA 与意见反馈

- QA 永久关联产生它的卡片版本；切换当前分析版本时不得级联删除旧卡片或 QA。
- 新版本卡片的追问区从空白开始，不把针对旧内容的 QA 自动展示在新内容下方。
- 用户已经打开旧详情页时可以继续查看与追问该旧版本，关闭后信息流使用当前版本。
- 意见反馈永久关联提交时的卡片版本、生成内容、模型和 Prompt 快照。
- 反馈导出继续包含当时的场景、音频信息、完整转写和完整 QA。
- 第一阶段不提供前端版本切换页面，但底层必须可完整溯源。

## 10. 待办保护与匹配

模型重新生成的是待办候选。待办必须保存以下来源与用户状态：

- 来源原始 `job_id`、事件 ID 和证据片段；
- 标准化行动、对象、负责人和截止时间；
- `user_edited`；
- `completion_source=user|model`；截止时间过期不是完成来源；
- 用户删除墓碑及其稳定来源指纹。

发布时执行：

- 未被用户操作且稳定来源匹配的旧待办可以更新模型文本和截止时间；
- 用户编辑过的待办保留用户文本与截止时间；
- 用户手动完成的待办保持完成，并保留用户完成来源；已过期但未完成的待办继续保持未完成，标红并在未完成区优先展示；
- 用户删除过的待办不能因重分析复活；
- 新分析发现且未命中现有待办或删除墓碑的候选正常新增；
- 只有来源事件、标准化行动、负责人和兼容截止时间均匹配时才合并；
- 无法可靠匹配时保留旧待办，将新候选作为独立待办，禁止强行合并。

删除墓碑随「清除所有历史」一并删除。

## 11. 隐藏画像的确定性重建

历史重分析采用两阶段画像策略：

1. 整个批次的场景分析都只使用批次开始时冻结的同一份画像快照，禁止前一条重分析结果影响后一条；
2. 所有可处理项结束后，基于每个原始上传批次的当前已发布分析版本统一重建隐藏画像。

这样处理顺序不会改变结果，也不会让早期误判在同一批次中自我强化。

画像重建在独立事务中生成候选画像，成功后一次性替换当前画像。失败时旧画像继续生效，批次状态标记为 `content_completed_profile_failed`，并支持只重试画像，不回滚已成功发布的卡片。

## 12. 统一任务调度与并发

普通上传模型分析、历史重分析和清除历史必须使用同一个 `AnalysisTaskCoordinator`：

- 第一阶段同一时刻只执行一个远程模型任务，避免限流、画像竞争和费用叠加；
- Whisper 本地转写可以与历史重分析并行；
- 新上传完成 Whisper 后，其模型分析优先于历史队列；
- 新上传模型分析期间，历史批次停止领取下一项，完成后自动继续；
- 同一原始上传批次不能同时被普通重试和历史批次处理；
- 历史重分析运行或暂停时禁用「清除所有历史」；
- 清除历史必须先确认没有远程模型任务运行，再在统一锁内删除数据库和音频文件；
- 同一时刻只允许一个历史重分析批次处于 `running|paused|stopping`。

## 13. 停止、恢复与状态

历史批次与每个原始上传项持久化以下状态：

- 批次：`pending|running|paused|stopping|completed|completed_with_failures|content_completed_profile_failed|stopped`；
- 项目：`pending|running|succeeded|failed|stopped`。

运行期间顶部入口展示进度，并提供「停止重新分析」：

- 停止请求不强制中断正在进行的厂商请求；
- 当前原始上传批次完成或失败后停止领取下一项；
- 已成功发布的版本保留，未处理项变为 `stopped`；
- 再次操作时确认窗口允许「继续剩余项目」或「按当前配置重新开始全部历史」。

服务异常退出后，下次启动把 `running` 项恢复为 `pending` 并继续原批次快照。用户关闭浏览器不影响本地后端任务。

## 14. 厂商错误、重试与恢复

- 创建批次前校验当前厂商一次，不为每个历史项额外发起独立校验请求；
- 模型调用返回认证失效、余额不足、Keychain 不可访问或限流时，在当前项安全结束后暂停整个批次；
- 用户重新校验成功、保存新 Key 后确认继续，或限流倒计时结束并由后台校验成功后恢复；
- `credential_generation` 改变时必须再次确认，不能静默切换账户凭据；
- 网络超时采用有限重试，最多两次并使用退避；
- Schema 修复最多一次；
- 不对认证、余额不足或明确的内容拒绝自动重试；
- 单条普通模型响应异常只标记该项失败，继续后续项目；
- 日志只保存归一化错误，禁止写入 API Key 或未脱敏厂商响应。

## 15. 进度与完成提示

前端展示批次总数以及 `成功/失败/待处理/已停止` 数量，不能只展示一个模糊的 `X/Y`。

完成提示：

- 全部成功：`已用最新 Prompt 重新分析 N 次历史上传`；
- 部分失败：`已完成 S 次，F 次分析失败，失败项旧结果已保留`；
- 全部失败：`重新分析失败，历史结果未发生变化`；
- 用户停止：`已停止；已完成 S 次，剩余 R 次未处理`；
- 内容完成但画像失败：`历史内容已更新，个性化画像更新失败，可重新尝试`。

## 16. 数据保留与清理

- 原始音频和结构化转写只有一份，分析版本不得复制它们；
- 旧分析版本保存结构化 JSON、模型和 Prompt 快照、QA 与反馈关联；
- 普通信息流只查询 `current_analysis_version_id`；
- 「清除所有历史」删除全部原始上传、分析版本、QA、待办、删除墓碑、隐藏画像和本地音频；
- Prompt 配置、API Key 配置和已导出的意见反馈文件仍按原规则保留；
- 第一阶段不自动清理旧分析版本，产品后续根据真实磁盘增长决定是否增加版本清理入口。

## 17. API 边界

- `GET /api/history/reanalysis-batches/preview`：返回上传批次数、文件数、字符数、模型、Prompt 快照摘要、预计调用范围和启动阻断原因。
- `POST /api/history/reanalysis-batches`：使用预览对应配置创建批次；重复请求返回现有运行中批次。
- `GET /api/history/reanalysis-batches/current`：返回批次状态、当前项和各状态数量。
- `POST /api/history/reanalysis-batches/{id}/stop`：请求在当前原始上传项结束后停止。
- `POST /api/history/reanalysis-batches/{id}/resume`：在凭据和快照校验通过后继续剩余项目。
- `POST /api/history/reanalysis-batches/{id}/retry-profile`：只重试画像重建。

预览接口返回短时有效的 `preview_token` 和快照摘要哈希；创建批次必须携带该令牌。如果厂商、凭据代次、Prompt、历史范围或画像快照在预览后变化，创建接口返回配置已变化，要求用户重新确认，避免确认内容与实际费用范围不一致。

所有创建与控制接口要求幂等键，并实施本地 Web 安全边界：服务只监听 loopback、严格校验 `Origin`/`Host`、拒绝跨站请求，并要求网页启动时获得的随机本地会话令牌。不能只依赖“服务运行在 localhost”，防止恶意网页静默触发会产生费用的批量分析。接口只引用现有 `job_id` 和结构化转写，不接收音频文件上传。

## 18. 验收标准

1. 三个页面顶部均显示入口，且位于「清除所有历史」左侧。
2. 无历史数据时入口禁用，不能创建空批次。
3. 确认窗口准确显示上传批次数、音频文件数、当前模型、Prompt 版本、调用范围和费用提醒。
4. 同一次上传的多个文件只生成一个新分析版本，不拆分、不重复。
5. 重分析期间 Whisper 与说话人识别调用次数均为零。
6. 批次使用完整 Prompt、哈希、模型、凭据代次和画像快照，运行中修改配置不会静默影响结果。
7. 每个原始上传批次全部成功后原子切换版本，不出现重复、混搭或空窗。
8. 新 Prompt 不生成的场景从当前信息流消失，但旧卡片、QA 和反馈仍可溯源。
9. 单条失败时旧版本仍可查看，其他历史项继续处理。
10. 新版本不自动展示旧版本 QA；已打开旧详情不会被强制关闭。
11. 用户编辑、完成、删除过的待办状态不被重置，删除待办不复活。
12. 所有历史项使用同一画像快照，调换处理顺序不会改变画像输入。
13. 新上传模型分析优先，历史任务自动让路并继续。
14. 历史批次运行或暂停时不能清除历史。
15. 停止操作不会开始新项目，已成功项目不回滚。
16. 页面刷新、浏览器关闭和服务重启后状态与检查点可恢复。
17. 厂商失效或凭据代次变化时批次暂停，不静默使用新凭据。
18. 重分析不改变原内容的自然日和信息流排序。
19. 意见反馈导出仍包含当时版本的生成内容、转写和完整 QA。
20. 任何日志、接口响应和批次记录均不包含 API Key。
21. 五十次连续历史重分析不会复制音频或转写文件。
22. 预览后配置发生变化时不能直接创建批次，必须重新确认。
23. 非本地同源网页无法调用创建、停止或恢复接口。
24. 更换 Key 后继续时，当前未发布项不会混用两代凭据的场景检查点。

## 19. 第一阶段不做

- 不重新执行 Whisper 或说话人识别；
- 不提供前端新旧版本切换与差异对比；
- 不支持按日期、场景或单个上传批次筛选刷新；
- 不并行执行多个历史批次或多个远程模型任务；
- 不在保存 Prompt 后自动刷新历史；
- 不提供单个场景局部发布；
- 不自动清理旧分析版本。
