# Audio Memory 历史音频批量重分析设计

**状态：** 已确认，待实施计划

## 1. 目标

用户频繁修改六场景 Prompt 后，可以使用当前模型和最新 Prompt 重新处理全部历史音频，而不重新上传音频、不重新执行 Whisper 转写或说话人识别。

该功能用于缩短 Prompt 迭代周期。它只重跑模型相关阶段，不能修改或删除原始音频、结构化转写、反馈与追问记录。

## 2. 入口与状态

- 顶部导航新增「重新分析全部历史」，位于「清除所有历史」左侧。
- 该入口在信息流、音频历史和 Prompt 设置三个页面始终可见。
- 没有任何已完成历史音频时，按钮禁用。
- 已有批量重分析任务运行时，按钮显示「重新分析中 X/Y」并禁止重复启动。
- 普通单次上传分析不阻止用户查看入口；若存在正在分析的新上传任务，确认窗口说明该任务不属于本次历史批次。

## 3. 确认窗口

点击入口后弹出确认窗口，包含：

- 待重新分析的历史音频数量；
- 当前模型厂商与模型名称；
- 当前六场景 Prompt 版本；
- 「不会重新转写音频」说明；
- 「会调用当前模型并产生 API 费用」提醒；
- 取消与「开始重新分析」按钮。

当前厂商未配置、不可用或正在校验时，不允许启动。用户可关闭窗口并前往模型配置。

## 4. 处理范围与快照

用户确认时，系统创建一个批次快照，固定：

- 批次内所有已完成历史音频 ID；
- 当前厂商、模型 ID 与模型配置版本；
- 系统 Prompt、公共 Prompt、事件地图 Prompt 和六场景 Prompt 版本；
- 创建时间与总任务数。

确认后新增的音频不进入该批次。批次运行期间修改 Prompt 或切换厂商，不影响正在运行的批次；下次新建批次才使用新配置。

第一期只处理已经完成并进入音频历史的音频。未完成、失败或被放弃的上传任务不进入批次。

## 5. 重分析链路

每条历史音频复用：

- 原始音频记录；
- 结构化转写文字；
- 词级时间戳与片段 ID；
- 说话人识别结果；
- 录制日期、时区和其他可靠元数据。

用户只能编辑六场景自然语言 Prompt。事件地图存在、已通过证据校验且固定事件地图 Prompt 与 Schema 版本未变化时，必须复用该事件地图，并重新执行：

1. 六场景模型分析；
2. Schema 与证据完整性校验；
3. 隐藏画像增量计算；
4. 卡片与待办候选生成。

如果历史事件地图缺失、版本不兼容、引用了不存在的转写片段，系统重新生成事件地图后再执行六场景分析。任何情况下都不重新执行 Whisper 或说话人识别。

## 6. 发布与旧结果保护

- 每条音频的新六场景结果全部成功并通过验证后，才在一个数据库事务中替换该音频的旧模型结果。
- 新分析失败时继续展示该音频的旧结果，并记录失败原因。
- 批次中一条音频失败，不阻塞其他音频。
- 信息流不得出现同一音频的新旧两套重复卡片。
- 批次开始时不提前删除旧卡片，避免长任务期间页面内容消失。

## 7. 待办、画像、反馈与追问

### 7.1 待办保护

模型重新生成的是待办候选，发布时按来源音频、来源事件、标准化行动、负责人和截止时间进行匹配：

- 未被用户操作的旧待办可以被新分析内容更新；
- 用户手动编辑过的待办保留用户文本和截止时间；
- 用户已完成的待办继续保持完成；
- 用户删除过的待办保存删除墓碑，不因重分析重新出现；
- 新分析发现且未被墓碑命中的待办正常新增；
- 无法可靠匹配时保留旧待办，并把新候选作为独立待办，禁止模型强行合并。

### 7.2 隐藏画像

批次完成后，基于当前所有已发布分析结果重新构建隐藏画像。画像重建失败不回滚已经成功替换的单条卡片，但旧画像继续生效，并将批次标记为「内容完成、画像更新失败」，允许单独重试画像。

### 7.3 反馈与追问

- 历史意见反馈和追问永久保留，关联到它们产生时的分析版本；
- 重分析不会把旧反馈错误绑定到新卡片版本；
- 反馈导出继续包含当时的生成内容、转写原文、场景和完整 QA；
- 第一阶段不在前端提供新旧分析版本切换页面。

## 8. 进度、暂停与恢复

- 后端持久化批次与每条音频的 `pending/running/succeeded/failed` 状态。
- 前端轮询或订阅批次状态，展示 `正在重新分析 X/Y`。
- 用户离开页面、刷新网页或关闭浏览器后，本地后端继续处理。
- 本地服务异常退出后，下次启动将 `running` 项恢复为 `pending` 并继续批次。
- 第一阶段不提供手动暂停按钮；停止本地服务等同于暂停，重新启动后自动继续。
- 再次点击已结束批次的入口会创建新批次；若上次存在失败项，确认窗口同时说明失败数量，但新批次仍按当前全部历史重新处理。

## 9. 完成提示与错误处理

批次结束后展示：

- 全部成功：`已用最新 Prompt 重新分析 N 条历史音频`；
- 部分失败：`已完成 S 条，F 条分析失败，旧结果已保留`；
- 全部失败：`重新分析失败，历史结果未发生变化`。

错误按厂商认证失败、余额不足、限流、网络超时、模型响应异常、Schema 校验失败和本地存储失败归一化。认证、余额或限流问题出现时停止领取新任务，保留当前进度，待当前厂商恢复可用后继续，避免对剩余音频制造重复失败和额外费用。

## 10. 数据与版本记录

每个新分析版本至少记录：

- `analysis_version_id`；
- 来源音频与原始分析任务 ID；
- 批量重分析批次 ID；
- 模型厂商、模型 ID 和模型配置快照；
- 六场景 Prompt 版本与固定 Prompt 版本；
- 事件地图版本与是否复用；
- 创建时间、完成时间和状态；
- 归一化失败代码，不保存 API Key 或厂商原始敏感响应。

旧分析版本保留在本地数据库中用于反馈溯源和未来模型对比，但普通信息流只读取当前发布版本。

## 11. API 边界

- `POST /api/history/reanalysis-batches/preview`：返回数量、当前厂商、模型和 Prompt 版本以及是否允许启动。
- `POST /api/history/reanalysis-batches`：创建批次并返回批次 ID；同一时刻只允许一个运行中批次，重复请求返回现有批次。
- `GET /api/history/reanalysis-batches/current`：返回批次总数、各状态数量和当前处理项。
- 批次只引用现有结构化转写，不接收音频文件上传。

## 12. 验收标准

1. 三个页面顶部均显示入口，且位于「清除所有历史」左侧。
2. 无历史数据时入口禁用，不能创建空批次。
3. 确认窗口准确显示数量、当前模型、Prompt 版本和费用提醒。
4. 修改 Prompt 后重分析全部历史，Whisper 与说话人识别调用次数均为零。
5. 批次运行期间修改 Prompt 或切换模型，不改变批次快照。
6. 单条新分析成功后原子替换旧卡片，不出现重复或空窗。
7. 单条失败时旧卡片仍可查看，其他音频继续处理。
8. 页面刷新和浏览器关闭后任务继续；服务重启后任务可恢复。
9. 用户编辑、完成、删除过的待办状态不被重置，删除待办不复活。
10. 意见反馈和完整 QA 仍关联原分析版本，不被覆盖。
11. 当前厂商失效时停止领取新任务，恢复后可以继续。
12. 任何日志、接口响应和批次记录均不包含 API Key。

## 13. 第一阶段不做

- 不重新执行 Whisper 或说话人识别；
- 不提供新旧分析版本切换与差异对比；
- 不提供按日期、场景或单条音频选择刷新；
- 不提供多个批次并行运行；
- 不自动在保存 Prompt 后刷新历史；
- 不提供手动暂停按钮。
