# Beta 8 两层事实索引设计

**日期：** 2026-09-07
**状态：** 用户已批准，2026-09-08 已完成离线实施与验证
**替代边界：** 本文批准后，替代《Beta 8 活动会话索引设计》中“单层 `activity_sessions[].ranges` 同时承担事件语义和全文覆盖”的部分。

## 1. 决策摘要

Beta 8 索引改为两层：

1. **互斥覆盖账本**：证明每个可靠转写片段都已被看见，并且只有一个主要时间线归属或明确排除原因。
2. **事实事件目录**：记录真实发生的主要活动和其中嵌入的内容。事件的证据可以合理重叠，但不能因为话题、录音文件或活动阶段变化而伪造多次独立沟通。

索引是 V1 的防漏、定位和主体校验导航，不是报告、场景分类结果或写作提纲。V1 仍必须获得完整逐字稿；索引不得取代事实输入边界。

## 2. 要解决的问题

单层索引让模型为每个事件独立填写起止 range。这导致两类概念被混合：

- “这段时间的主要活动是什么”；
- “这个事件由哪些片段提供证据”。

结果是单个 range 均合法，但不同事件的 range 可以嵌套或重复。真实 Pro 输出已出现：

- “短视频浏览”包含“英雄联盟游戏”整段区间；
- 一个车辆电话单元包含另一个电话单元；
- 一场跨文件工作坊被按文件、分享和讨论阶段拆成多个工作沟通。

这些错误不能通过继续增加 Prompt 可靠消除；数据契约必须先区分“覆盖”和“事件证据”。

## 3. 目标

1. 每个可靠转写片段都在覆盖账本中恰好出现一次。
2. 已知不可靠片段由本地代码处理，不要求模型猜测。
3. 有文字但属于噪声、重复、空内容或无法识别的片段可以明确排除。
4. 主要时间线不能出现空洞、重叠或嵌套。
5. 现实中同时出现的媒体声、游戏声、用户评论和第三方内容可以共享证据片段，不被迫伪装成互斥现实。
6. 一次真实电话、会议、工作坊或拜访只有一个主会话 ID，即使它跨文件或包含多个议题。
7. 工作沟通数量完全来自当次输入，不设固定数量。
8. 保持索引输出精简，不在索引中写报告、建议、待办或搜索任务。

## 4. 非目标

索引不负责：

- 决定最终卡片数量；
- 将全部事实强制分配到七个报告场景；
- 评估用户发言或事件的价值；
- 生成 Markdown、建议、待办、搜索请求或修订指令；
- 推断人格、动机、疾病、深层原因或他人心理；
- 只因为出现离职、薪资、年假、职业选择或公司话题就判定为工作沟通；
- 使用人工 Ground Truth 生成、修改或合并模型索引。

## 5. 核心概念

### 5.1 主会话 `primary_sessions`

主会话表示时间线上用户正在参与或所处的主要活动，例如电话、工作坊、午餐聊天、家庭互动、玩游戏、观看内容或独自表达。

每个主会话包含：

- `session_id`；
- `activity_kind`；
- `communication_purpose`；
- `participation_mode`；
- `subject`；
- 一句中性 `description`；
- `start_boundary`、`end_boundary`；
- 起止边界的证据片段 ID。

主会话本身不由模型填写结束 range。它的实际范围由覆盖账本中指向该 `session_id` 的块确定。同一 `session_id` 可在同一文件或多个文件中出现多次。

### 5.2 嵌入事件 `embedded_events`

嵌入事件表示主活动中同时出现、但不应被冒充成另一段互斥时间线的内容，例如：

- 游戏过程中的游戏播报；
- 午餐聊天中提到的第三方案例；
- 观看媒体时的用户评论；
- 工作坊中播放的 Demo 或被讨论的外部内容。

每个嵌入事件包含：

- `event_id`；
- `parent_session_id`；
- `event_kind`；
- `expression_mode`；
- `subject`和一句中性 `description`；
- 一个或多个 `evidence_ranges`。

`evidence_ranges` 可以与父会话覆盖区间重叠，也可以与其他嵌入事件重叠；但必须完全位于父会话的实际覆盖内。

### 5.3 互斥覆盖账本 `file_timelines`

每个输入文件只有一条时间线。模型按转写片段顺序输出 block 起点，不输出结束点。

每个 block 只能是：

- `session`：指向一个 `primary_sessions[].session_id`；
- `excluded`：原因为 `noise`、`duplicate`、`unintelligible` 或 `empty`。

服务端要求：

1. 每个文件的第一个 block 必须从该文件第一个可靠片段开始；
2. block 起点必须引用该文件中存在的可靠片段；
3. block 起点必须严格递增，不得重复、倒序或跨文件；
4. 前一 block 的结束点由“下一 block 起点之前的最后一个可靠片段”确定；
5. 最后一个 block 延伸到该文件最后一个可靠片段；
6. 已被本地转写质量逻辑标记为不可靠的片段不交给模型分配，由程序在规范化索引中记录；
7. 时钟上存在、但没有任何转写片段的静音区间不伪造 segment ID，也不进入片段覆盖账本。

这一层从结构上消除空洞和重叠：模型无法为同一 block 填写两个结束位置，也无法用一个超长 range 包住其他 block。

## 6. 模型输出契约

模型只输出一个精简 JSON 对象，逻辑形状如下：

```json
{
  "input_complete": true,
  "input_error": null,
  "primary_sessions": [
    {
      "session_id": "session_workshop_1",
      "activity_kind": "conversation",
      "communication_purpose": "work",
      "participation_mode": "user_present_live_interaction",
      "start_boundary": "contact_started",
      "start_boundary_evidence_segment_ids": ["seg_1_1320"],
      "end_boundary": "contact_ended",
      "end_boundary_evidence_segment_ids": ["seg_2_2175"],
      "subject": "产品工作坊",
      "description": "参与者围绕产品方向、演示和实现约束持续讨论。"
    }
  ],
  "embedded_events": [
    {
      "event_id": "embedded_demo_1",
      "parent_session_id": "session_workshop_1",
      "event_kind": "content_playback",
      "expression_mode": "media_playback",
      "subject": "产品演示",
      "description": "工作坊中播放并讨论了一段产品演示。",
      "evidence_ranges": [
        {
          "source_file": "file-3.mp3",
          "start_segment_id": "seg_2_30",
          "end_segment_id": "seg_2_80"
        }
      ]
    }
  ],
  "file_timelines": [
    {
      "source_file": "file-2.mp3",
      "blocks": [
        {
          "start_segment_id": "seg_1_0",
          "disposition": "excluded",
          "excluded_reason": "empty"
        },
        {
          "start_segment_id": "seg_1_3",
          "disposition": "session",
          "session_id": "session_call_1"
        }
      ]
    }
  ]
}
```

实际 Schema 必须使用严格的判别联合：

- `disposition=session` 时必须有 `session_id`，且不得有 `excluded_reason`；
- `disposition=excluded` 时必须有 `excluded_reason`，且不得有 `session_id`；
- 非对话主会话的 `communication_purpose` 必须为 `not_applicable`；
- 预录、广播或媒体内容不得标记为用户实时交互；
- 主会话 ID、嵌入事件 ID 和文件时间线必须唯一；
- 所有引用 ID 必须存在。

数量上限保持精简而不限制报告价值：

- 最多 128 个主会话；
- 最多 256 个嵌入事件；
- 每个文件最多 256 个 block，全局最多 512 个 block；
- 每个嵌入事件最多 32 个证据 range；
- `subject` 最长 120 字符，`description` 最长 300 字符且只写一句中性事实。

真实输入超出契约上限时必须返回 `event_index_limit_exceeded`，不得为满足上限而错误合并事件。

## 7. 边界规则

### 7.1 对话边界

同一主会话内：

- 议题变化不拆分；
- 从分享进入讨论不拆分；
- 录音文件切换不拆分；
- 职业、薪资、离职或年假话题不自动改变沟通目的；
- 短暂停顿不拆分。

只有证据表明前一次联系真正结束，且后续发生新联系、新的参与者集合、散会后重新开始或主要活动切换，才能新建主会话。

当时间线中相邻两个 block 均指向对话会话，且 `session_id` 不同时，两个会话必须分别提供结束与新开始的证据片段。服务端检查证据 ID 是否存在且位于边界附近；证据语义由 Prompt 和评测门禁检查。

### 7.2 工作沟通

工作沟通主会话必须同时满足：

- `activity_kind=conversation`；
- `participation_mode=user_present_live_interaction`；
- `communication_purpose=work` 或 `mixed`。

工作沟通数量是当次输入的模型结果。生产逻辑不知道也不检查固定数量。特定验收样本可在模型输出完成后使用隐藏 Ground Truth 判分，但 Ground Truth 不传给模型，也不用于修改索引。

## 8. 本地规范化和持久化

模型输出先解析为“索引草稿”，再由本地纯函数生成“规范化索引”：

1. 根据每个文件中严格递增的 block 起点生成互斥起止 range；
2. 将指向同一 `session_id` 的多个 block 收集为该主会话的规范化 ranges；
3. 将 `excluded` block 转换为明确的排除 ranges；
4. 合并本地已知不可靠片段的系统排除记录；
5. 检查嵌入事件证据是否完全位于其父会话范围内；
6. 检查每个主会话和嵌入事件是否被真实引用；
7. 生成覆盖和边界诊断，任一错误均失败关闭。

只有规范化索引通过 Schema、引用、覆盖、边界和评测门禁后，才可作为 `beta8_event_index` 检查点持久化。模型原文继续先写入私有隔离目录。

## 9. V1 接口

V1 接收：

1. 完整可靠逐字稿；
2. 规范化主会话；
3. 嵌入事件及其证据；
4. 覆盖与排除账本；
5. 七场景能力和共享报告质量契约。

V1 仍负责：

- 将事实分配到主场景；
- 判断是否值得出卡；
- 写完整 Markdown；
- 生成候选搜索和候选待办；
- 对没有出卡的主会话或嵌入事件进行省略记账。

工作沟通闭包只针对符合工作沟通定义的 `primary_sessions`。嵌入的媒体问答、第三方案例或工作话题不得单独触发“一次工作沟通一张卡”。

## 10. 错误、修复和费用边界

- 索引草稿无效、block 起点非法、引用不存在、嵌入事件越出父会话或 Ground Truth 不通过时，不运行 V1。
- `--stop-after-index` 始终只允许一次底层请求，不执行自动覆盖修复或网络重试。
- 模型原始响应无论是否通过都先隔离保存，方便免费离线诊断。
- 不允许用 Ground Truth 修改、裁剪、合并或补全模型输出。
- 正常生产路径是否保留一次结构修复，必须作为独立费用策略明确配置，不得由 Schema 变更隐式开启。

## 11. 检查点、哈希和兼容性

- 新模型输出 Schema、规范化索引 Schema、Prompt、请求参数和规范化算法版本必须共同纳入 `fixed_rules_hash`。
- 旧 `activity_sessions[].ranges` 检查点在新哈希下自然失效，不隐式迁移。
- 旧付费原文继续作为失败证据保留，不伪装成新契约的成功检查点。
- 规范化索引可以提供受控的 `units` 兼容视图，供尚未迁移的 V1 闭包和审核代码使用；兼容视图只由本地规范化结果生成，不接收旧模型 JSON。

## 12. 验收标准

### 12.1 Schema 与规范化

- Schema 拒绝 block 同时存在 `session_id` 和 `excluded_reason`。
- Schema 拒绝 block 同时缺少两者。
- 规范化拒绝未知文件、未知片段、未知会话 ID、重复起点和倒序起点。
- 规范化从起点确定性生成无空洞、无重叠的完整覆盖。
- 规范化不为没有转写片段的静音时间伪造 ID。
- 嵌入事件可以与父会话共享证据，但越出父会话时必须拒绝。

### 12.2 事件语义

- 游戏、游戏播报和用户评论可以表示为一个主会话加嵌入事件，而不是三个互相重叠的主活动。
- 一场跨文件工作坊在多个文件中使用同一 `session_id`。
- 两次相邻电话可以是两个 `session_id`，但必须有可核验的结束和重新联系证据。
- 午餐期间谈到离职、薪资、年假或职业选择不自动变成新的工作沟通会话。
- 预录访谈和媒体问答不进入工作沟通闭包。
- 任意数量的真实工作沟通都可表达，生产 Schema 和 Prompt 中不出现样本专属数量。

### 12.3 V1 与费用保护

- V1 仍接收完整逐字稿，且能引用主会话和嵌入事件。
- 每个符合定义的工作沟通主会话恰好对应一张工作沟通卡；嵌入事件不单独触发该闭包。
- 每个可路由事实都被卡片引用或进入省略账本，不静默丢失。
- 旧检查点不会被新规则误复用。
- 索引单步验收最多只发生一次底层付费请求；失败不调用 V1。

### 12.4 免费回放和回归

- 将最新失败 Pro 原文作为反例 fixture，确认旧契约不能被当成新契约检查点。
- 使用人工构造的新契约等价输出，免费回放车辆两次电话、跨文件工作坊、游戏与嵌入媒体、午餐职业聊天和无效片段。
- Beta 8 全相关回归、供应商请求回归、dry-run、Prompt 字节一致性、固定规则哈希和 `git diff --check` 全部通过后，才可请求新的付费授权。

## 13. 实施边界

实施必须遵循 TDD，每个行为先以失败测试证明缺口，再进行最小生产修改。建议顺序为：

1. 新索引草稿 Schema；
2. block 起点规范化器；
3. 互斥覆盖和嵌入证据门禁；
4. Prompt 与 Composer；
5. Runner 隔离、规范化与检查点；
6. V1 引用和工作沟通闭包；
7. Ground Truth 评测适配；
8. 失败原文回放、全量回归和文档哈希更新。

在本规格通过用户审核之前，不实施生产代码，不调用付费模型。
