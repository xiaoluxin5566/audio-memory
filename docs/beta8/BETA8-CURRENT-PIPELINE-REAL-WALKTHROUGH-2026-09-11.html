1. 全链路和阶段职责

P0 转写

把音频变成可追溯原文

调用豆包录音文件识别 2.0，保留相对时间、segment 和说话人聚类。

输入：AAC/MP3
输出：完整转写
调用：每个音频 1 个 ASR 任务
P1 理解

高召回地理解内容

识别 Activities、Topics、Anchors、Attention Signals 和 Commitments，不做最终卡片取舍。

输入：一个完整转写窗口
输出：内容索引
调用：每窗口 1 次 DeepSeek
P2 规划

整合事件并决定什么出卡

只做三件事：Activity 整合与判断、Topic 出卡取舍、搜索需求。

输入：全部 P1 索引与可回读原文
输出：卡片计划 + research tasks
调用：固定 1 次 DeepSeek
P3 搜索

补充会改变决策的公开信息

按 P2 的独立 research task 聚焦搜索，验证原始页面和引文。

输入：公开化搜索问题
输出：查证结论 + 来源
调用：每任务 1–3 个子搜索，每个 1–2 次 Kimi 响应
P4 写作

用完整 Activity 原文写主卡

按场景 Prompt 选择表格、时间线、因果链、清单等表达，同时引用原文和搜索来源。

输入：卡片计划 + 完整源 Activity + P3
输出：Markdown 主卡
调用：每张卡 1 次 DeepSeek
P5 评分

独立验收每张主卡

按 15/15/25/30/15 评分，列出扣分项和缺失内容；不修改报告。

输入：主卡 + 计划 + 完整证据
输出：五维分数 + 扣分
调用：每张卡 1 次 DeepSeek

2. API 调用次数如何计算

DeepSeek 正常报告调用 = P1 窗口数 W + P2 的 1 次 + P4 卡片数 C + P5 卡片数 C
Kimi 搜索响应 = 研究任务数 R × 每任务 1–3 个聚焦子任务 × 每子任务 1–2 次响应
本次理论值 = 1 + 1 + 4 + 4 = 10 次 DeepSeek，Kimi = 0
本次账本值 = 11 次请求意图：10 次有效结果 + 1 次 P4 中断（是否计费不确定）

P1 窗口数由转写文本的 UTF-8 字节量与 80 KB 核心预算决定，不是按音频时长直接切。时长只会通过字数间接影响 W。

4. 为什么搜索是 0

当前 P2 的错误推理

  • 公司内部平台、人员和项目数据无法公开搜索。
  • 因此对 4 张卡全部判定 no_search。
  • P3 根本没有收到任务，Kimi 没有执行机会。

应当的判断

  • 内部事实不搜索。
  • 抽样方式、错误率、置信阈值等公开方法需要搜索。
  • P4 只能把公开方法作为建议补充，不得替换内部项目事实。
