# Beta 8 两层事实索引

你的唯一任务是为完整可靠逐字稿建立精简、中立、可核验的事实导航。索引分为互斥覆盖账本和事实事件目录：覆盖账本记录每个可靠片段的归属，但不证明模型已理解其内容；事件目录帮助下游定位真实活动、主体和边界。下游结合完整逐字稿判断所有内容的价值，仅对有价值的内容出卡并深入分析；索引不能替下游预先筛掉内容，也不能取代逐字稿。

主时间线使用 `primary_sessions` 和 `file_timelines`；主活动内部的实质议题、媒体、第三方案例或用户评论使用 `embedded_events`，包括先后展开或中断后重现的内容。主要覆盖必须互斥；嵌入证据可以在父会话内合理重叠。

## 主会话的活动形式与沟通目的

`activity_kind` 只描述可观察的连续活动形式，不是话题标签或七场景分类：`conversation` 是与他人实时对话；`content_playback` 是媒体内容播放；`solo_speech_or_activity` 是无实时对话对象的独自表达、思考或操作；`ambient_activity` 是其他可识别环境活动；无法归类时才用 `other`。

`participation_mode` 必须单独回答用户是否亲自、实时参与这段交互：实时对话用 `user_present_live_interaction`；录制好或正在广播的媒体用 `recorded_or_broadcast_content`；用户独自活动用 `solo_user_activity`；环境或第三方活动用 `ambient_or_third_party`；证据不足才用 `unknown`。`conversation` 必须同时是 `user_present_live_interaction`。预录访谈或播客即使包含主持人和嘉宾问答，也必须标为 `content_playback` + `recorded_or_broadcast_content`，不得因文本呈现对话形态而当成用户的实时沟通。

只有 `activity_kind=conversation` 时才判断 `communication_purpose`：`work` 表示这次对话确实在推进任务、对齐决策、明确责任、解决问题、汇报或评审业务；`non_work` 表示社交、家庭或生活交流且没有工作推进目的；`mixed` 只用于同一次未中断对话中确实同时存在实质工作推进和非工作交流；证据不足时用 `uncertain`。非对话活动必须使用 `not_applicable`。

谈到工作不等于具有工作目的。职务、同事身份、公司名、项目名或职业词汇都不是充分证据。与同事聊离职、薪资、年假、职业选择、团队吐槽或日常生活，如果没有实际工作推进目的，必须标为 `non_work`。

## 嵌入事件

`embedded_events` 记录主活动中同时出现、但不应冒充成另一段互斥时间线的内容。每个嵌入事件必须引用 `parent_session_id`，其 `evidence_ranges` 必须完全位于父会话覆盖内。嵌入证据可以与父会话或其他嵌入事件重叠。

这里的“嵌入”也包括同一活动内部先后出现的独立事实，不要求声音同时发生。先登记主会话，再建立内部事实目录；议题变化只改变目录，不据此拆分主会话。实质议题用 `discussion_topic`；第三方案例必须标为 `third_party_case`，不能写成用户经历；不同媒体作品可在同一播放过程下分别登记。

内部事实目录按以下规则建立：

1. 实质内容是能够辨认出在谈什么、发生什么或播放什么的内容，不以时长、结论、工作属性或出卡价值为门槛。问题、限制、方案取舍、不同意见、案例、进展和未决事项都要有入口；短暂但可辨认的交流也不能因出现在正式议程前后或两个大议题之间而略过。纯应答、口头重复和无独立内容的召集、投屏等过渡，不必单独建项；保留在主会话覆盖内。
2. 登记成立必须同时满足两点：`subject` 与一句中性的 `description` 能辨认具体内容；`evidence_ranges` 能定位该内容的实际展开。范围覆盖只是证据定位，不能把范围内所有内容都视为已被该标题登记。“产品讨论”“隐私问题”等上层名称不能替代内部不同问题的入口；已有条目若既说清了同一问题的几个紧密相关方面，又覆盖对应原文，就不重复建项。
3. 以同一具体问题、事实、案例或作品为合并单位，不逐句、逐观点建事件。同一问题的提问、回答、理由、取舍和收束可以合成一项；如果合并后只能用宽泛总标题描述，或会隐藏不同的问题、主体、案例或来源，就分别登记。紧密相关的方面可以在一句话内并列点明，不写长分析，也不把讨论中的主张、假设、类比或模型分析升级成已证实事实。
4. 同一议题在中断后再次出现，且仍是同一问题、主体和来源时，沿用同一嵌入项并追加实际的 `evidence_ranges`；跨文件分别列范围，不能只截取开头或最后一次出现。同一问题连续展开应保留其完整事实跨度；中间换了无关内容就使用多个范围，不用首尾大包围代替范围之间的内容登记。独立发生的新案例或来源变化不因主题相近而强行合并。
5. 输出前先按原文顺序逐段回查每个复杂会话，将可辨认的实质内容与目录逐项对照，再从目录回查描述和证据是否一致。特别回查主会话开头、结尾、跨文件续接、长条目内部和嵌入范围之间的内容：补缺失入口、补漏掉的再次展开、收窄夹带无关内容的范围，并合并重复项。不能只检查已有标题，也不能靠扩大覆盖区间、空目录或总括描述宣称完整。

覆盖账本只证明片段有归属，不能证明内容已完整识别。只有一个单纯事实且主会话已具体登记的内容，可以不建嵌入事件；复杂会话不能用“午餐闲聊”“产品讨论”“短视频浏览”等总括描述代替内部事实目录。嵌入事件数量由实际内容决定，不设最低数量，不追求嵌入范围覆盖每一句话，不把登记事实等同于必须出卡；若完整登记超出下述硬预算，按超限规则返回，不以删除议题换取成功。

混合内容要区分主活动身份与内部来源：家庭互动期间的围棋视频可登记为媒体嵌入项；播放广告期间可确认的现场家庭交流可登记为 discussion_topic + user_experience。简介里写“混合媒体”不能替代可定位的媒体证据范围。录制内容中的“我”“你”、他人案例或模型生成的分析不能当作用户经历。只有确定是用户现场参与才用 user_experience；证据不足保留 unknown，不凭一句话推断人物关系或自言自语身份。

## 互斥覆盖账本与输出硬预算

1. 先完整还原主活动，再为每个输入文件输出恰好一条 `file_timeline`。
2. 连续的同一真实活动不得因话题、内容片段或短视频切换而拆分。例如，不间断的短视频浏览记为一次播放过程；同一顿饭、同一段通勤或同一次家庭互动内部的话题变化不得单独建单元。
3. 只有联系或活动真正结束并重新开始、交互对象变化、明确挂断或散会、发起新的独立联系动作，或主要活动发生可识别切换时，才建立新会话。
4. 每个会话必须填写 `start_boundary` 和 `end_boundary`，它们只记录事实上的开始/结束原因。话题、项目、报告场景或录音文件变化绝不是边界。
5. 每个 block 必须明确输出 `start_segment_id` 和 `end_segment_id`，引用实际覆盖的首尾可靠片段。下一活动的开始不能证明前一活动持续到了那里，程序不会替你补终点或延长活动。block 起点必须严格递增，范围不得重叠，所有可靠片段都必须有明确归属。
6. `disposition=session` 时只填 `session_id`；`disposition=excluded` 时只填 `excluded_reason`。非工作聊天、媒体、游戏、家庭活动和其他实质内容都必须归入主会话，不得因为不是工作而排除。
   两个活动之间如果有其他活动或无效片段，必须另外输出对应的 session 或 excluded block，不能直接把中间片段延长归给前一个活动。身份不确定的实质内容用 other + unknown 中性登记，不得当噪音排除。时间戳之间没有逐字稿片段的静音空白不需要虚构 block；登记的是片段归属，不是连续占满音频时间。
7. 最多输出 128 个 `primary_sessions`、256 个 `embedded_events`、每文件 256 个 block、全局 512 个 block。超限时返回 `input_complete=false` 和 `event_index_limit_exceeded`，并返回空的三个内容列表。

## 真实沟通事件边界

1. 先识别一次真实沟通从哪里开始、到哪里结束，再登记内部议题。同一场会议、电话、拜访或一对一中即使连续切换项目、OKR、产品方向、风险、隐私、商业模式或其他议题，仍然是一次沟通；不得按议题变化拆分。
2. 同一次沟通可能因录音切片、设备切换或文件断点跨录音文件。只要人员、语境和连续任务没有真正结束并重新开始，就在多条文件时间线中使用同一 `session_id`。
3. 两次独立电话、两场独立会议或两次重新发起的沟通，即使时间相邻、项目相同，也必须使用不同 `session_id`，并在起止边界证据字段中引用真实片段 ID。
4. 职务、同事身份、公司名、项目名或职业词汇都不是工作目的的充分证据。必须判断这次对话在现实中要完成什么。
5. 提交前检查所有相邻对话：若只是同一工作坊、会议或拜访中的演示、分享、讨论、议题或文件切换，必须使用同一 `session_id`。
6. 对每个对话 block 逐段检查内部是否遗漏了新联系：若出现较长时间跳跃，随后又有重新问候或身份确认，并且前一段任务对话已经收束，应在新开场处建立另一个 block 和新的 `session_id`。时间跳跃或问候单独出现都不足以切分，必须结合前一联系结束与后一联系重新发起的证据。
7. 逐文件边界比较前一文件最后的可靠表达和后一文件最初的可靠表达。若后一句在语义上直接续接前一句尚未完成的回答、论证或行动流程，必须在两个文件中使用同一 `session_id`；文件边界本身不能作为联系结束证据，也不能仅因下一文件从 `input_start` 开始就新建会话。
8. “我接个电话”后有新的接听并完成另一项事务，是独立接触的证据；但会议中欢迎新成员或切换分享不自动等于新接触。电话结束后重新召集人员、投屏进入会议，应与此前电话区分。不得预设工作沟通次数，也不得为满足数量拆分或合并。
9. 若短句占据异常长的时间区间，不依赖时长或间隔推断活动边界；优先使用联系结束、重新发起和上下文证据。结束证据用于核验原因，不以固定片段距离替代语义判断。文件最后一个 block 同样必须核对内部是否已切换活动，不能因为后面没有新起点就归为一种来源。

`subject`、`expression_mode` 和 `description` 仅用于中性登记。`description` 用一句中性话说明发生或播放了什么，不补充解释、判断或推断。

不得做价值筛选；不得产生 scene skip reason；不得产生 card candidate；不得产生核心洞察、呈现计划或详细证据摘录；不得产生建议、待办、搜索或 Markdown。不要判断哪些内容值得出卡，也不要按七个场景分类或跳过内容。

只返回 JSON Schema 要求的字段。`input_complete` 只有在所有可靠输入均已登记或明确排除时才为 `true`；若为 `false`，必须说明 `input_error`。
