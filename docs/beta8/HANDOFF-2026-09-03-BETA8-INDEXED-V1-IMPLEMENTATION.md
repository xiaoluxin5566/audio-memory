## 2. 用户已确认的架构判断

### 2.1 V1 正常路径采用两次调用

不再要求一次调用同时完成全量发现、七场景分类、价值判断、主体归属、跨卡去重和完整长文写作。

但也不采用“详细规划＋长文写作”。旧实验已证明详细规划容易耗尽 32,000 输出 Token。

新方案是：

1. 第一次只做薄的全量事实索引；
2. 第二次做完整 V1 写作；
3. 索引不是写作计划，也不是第二次的输入上限；
4. 审核只负责验证和纠错，不用来把粗糙草稿重写成好报告。

### 2.2 两次调用的 Prompt 都要重新实施

实施时不直接沿用 X/Y 实验 Prompt。

**第一次 Prompt：**

- 新建正式 `event-index.md`；
- 必须登记播客、媒体播放、第三方案例、低价值但实质存在的内容单元；
- 禁止价值筛选、场景跳过理由、卡片候选、核心洞察、建议、搜索、待办和 Markdown；
- 只输出单元 ID、文件、起止片段、类型、主体、表达用途和一句中性描述。

**第二次 Prompt：**

- 新建正式 `all-scenes-v1.md`；
- 必须把完整共享质量契约与七份场景黄金能力编译进 instructions；
- 不得再把完整结构规则压缩成“适当使用表格、列表”；
- 直接产生可展示的完整 V1，不生成待审核扩写的粗糙草稿。

## 5. 必须全部落地的报告优化方向

### 5.1 工作沟通是真实沟通事件，不是议题卡

- 一次会议、拜访、电话、线上沟通、一对一、面试、客户或供应商交流，各对应一张“工作沟通”卡。
- 同一沟通的多个议题放在卡内小标题中，不拆卡。
- 同项目的两次独立沟通不能误合并。
- 录音文件切换不等于沟通切换，同一沟通可跨文件。
- 无沟通对象的个人工作思考不自动当作工作沟通；它只在有独立价值时成卡。

### 5.2 非工作卡只按价值出卡，不设数量上限

- 不使用“最多 5 张”或任何其他配额。
- 仅仅发生过、可以做简单计算、出现情绪词或能套通用建议，都不是出卡理由。
- “2026 年 9 月 7 日生日撞上开学，需先确认星期几”类只有简单日期计算、没有独立帮助价值的内容不成卡。
- 一旦价值成立，就必须把卡片写丰富，不能只用几句话占位。

### 5.3 主体、对象和表达用途必须按完整语义判断

必须综合判断：

- 谁在表达；
- 在讲谁；
- 是本人经历、转述、引用、案例介绍、媒体播放还是模型输出；
- 当前表达是为了解释什么；
- 用户是否明确把第三方内容联系到自己。

用户在周会中讲陈震的经历，用于说明产品思路时，这是工作沟通论据，不是用户本人的心理状态。但如果用户在任何语境中确实表达自己的离职、疲惫、心理疏离或犬儒体验，证据足时仍可以分析。不对人名、场景或关键词写特判。

### 5.4 卡片必须同时做到丰富和可快速阅读

- 标题后立即给核心洞察或核心信息组，不限制为一句。
- 核心信息之后再给必要事实、论据、分析、分歧、权衡、影响、已知、未知和帮助。
- 丰富是高信息密度和真正帮助，不是重复或凑字数。
- 复杂内容不得堆成一整段。

### 5.5 内容类型必须匹配呈现方式

| 内容类型 | 优先呈现方式 |
|---|---|
| 多项结论 | 要点列表或结论表 |
| 多个议题 | 分级小标题 |
| 方案比较 | 对比表 |
| 时间推进 | 时间线 |
| 因果关系 | 因果链，并区分事实、推断和待验证环节 |
| 明确行动 | 行动表 |
| 风险与应对 | 风险—影响—对策表 |
| 沟通建议 | 符合对象、语境和目标的可复制话术 |
| 复盘建议 | 可直接填写的记录模板 |
| 操作建议 | 有先后顺序的分步骤清单 |
| 单一深入判断 | 短段落加证据、边界和验证方式 |

这张表必须完整进入 V1、审核和定向修订的实际 instructions，不得只存在设计文档。一张卡可组合多种形式；简单内容不为格式而凑表格。

### 5.6 建议必须给出可直接使用的载体

不能只写“继续保持”“多关注”“加强沟通”“建议记录一下”。建议应根据当前情境给出：

- 什么时候做；
- 具体做什么；
- 如何记录或验证；
- 为什么适合当前问题；
- 可直接使用的表格、话术、模板、清单、步骤、小实验或示例。

这是所有卡片的全局要求，不是只针对自我成长。

### 5.7 文字必须直接对用户说

- 先给结论，再给论据。
- 不以“这份记录围绕”“从这段记录可以看出”“你从一段记录中看到”“分析指向”“逐字稿中提到”开头。
- 不把用户写成被研究对象。
- 不在用户可见正文暴露录音、片段 ID、置信度、模型过程和搜索过程。

### 5.8 Markdown 和前端必须同时修复

- 模型生成的 H2–H4 不得带 `一、`、`1.`、`1、`、`（一）` 等手工序号。
- 前端是章节自动编号的唯一负责方。
- 页面卡片头已经显示标题时，Markdown H1 不再重复显示。
- 历史卡片先做展示层序号兼容，不覆盖原始 Markdown。
- 窄屏上表格允许横向滚动，小标题、正文、列表、表格和引用具有清晰层级。

## 6. 七场景已确认能力不能在统一写作中丢失

### 6.1 `work_communication`

- 按真实沟通次数成卡。
- 工作沟通卡不是空洞会议纪要，需展示核心结果、分歧、权衡、未决问题和真实行动。
- 个人工作思考只按独立价值出卡。

### 6.2 `parenting_family`

- 还原互动问题，做证据充分、强度匹配、可验证的分析。
- 建议应包含具体步骤或可复制话术。
- 不从文字猜测音量、表情、肢体、沉默时长、私下动机或谁对谁错。
- 不贴性格、疾病或长期关系类型标签。

### 6.3 `health_state`

- 同时关注身体和心理状态。
- 困倦、长时间吐槽/宣泄和反复低强度信号不应被机械删除。
- 可以分析趋势、触发、维持环路、恢复和可能关联，但不做医疗/心理诊断，不把相关当因果，不建议擅自改处方。

### 6.4 `content_consumption`

- 内容消费不默认等于学习。
- 播客、视频、节目、音乐或自动播放内容必须先与用户自身表达分离。
- 媒体中的观点不自动成为用户观点。
- 不能因第一次索引做价值过滤而漏掉播客。

### 6.5 `inspiration_insight`

- 先接住灵感、理解目标、充分发散，再目标导向收敛到关键假设和验证。
- 所有卡的目的是帮助用户，不是批判用户。
- 模型扩展不能写成用户原本想法或已接受计划。

### 6.6 `self_growth`

- 只分析当前报告期有证据的自我理解。
- 一次具体强表达或多个独立事件可以成立，但不把一次情绪、孤立观点或模型编造的深层故事写成成长卡。
- 自我成长建议必须给记录模板、小实验、验证问题或其他具体工具。

### 6.7 `life_decisions`

- 是非工作现实目标的决策与执行顾问，不是待办聚合器。
- 证据足时给直接建议；关键信息缺失时给当前最佳的条件化判断。
- 使用选项、判断标准、权衡、待验证信息和下一步，不做空泛 pros/cons 列表。

## 7. 后续审核、搜索、修订不能与 V1 混淆

### 7.1 V1 与审核的区别

- 第二次 V1 写作必须自己做到丰富、清晰、具体和可展示。
- 统一审核只发现事实、归属、遗漏、价值、结构和帮助性问题，不重写正文。
- 全局编辑审核只输出 `keep/revise/merge/drop/create`、修订要求、搜索任务和待办取舍，不生成第二份完整报告。
- 定向修订只改受影响卡，`keep` 卡 Markdown 字节级不变。

### 7.2 新发现的实施缺口

当前 `Beta8PromptComposer.compose_revision()` 把 `target_scene_prompt` 放在 untrusted user data 中，而不是 instructions 中。这可能使定向修订丢掉目标场景特色和新的质量要求。

实施必须改为：

- 共享质量 Prompt 进 instructions；
- 目标场景 Prompt 进 instructions；
- source cards、revision task、transcript segments 和 search packets 保留在 untrusted data；
- 用 Composer 测试断言 V1、审核和修订都真正携带完整共享质量契约。

### 7.3 待办边界

- 只有用户已明确决定、接受、安排或承诺的行动，以及虽由他人执行但用户有真实跟进责任的事项，才能进待办。
- 模型建议、搜索建议、普通愿望、开放问题、已完成事项和无需用户跟进的他人任务不是待办。
- 每个输入待办候选必须恰好进入一个全局待办，或进入 `dropped_todo_candidates` 并说明原因。

### 7.4 搜索逻辑本轮冻结

用户已明确“搜索逻辑先不改”。因此本轮：

- 不改搜索候选产生逻辑；
- 不改搜索任务数量逻辑；
- 不改 Kimi 2.6 原生搜索执行方式；
- 不改搜索结果采用逻辑；
- “搜索 10 个、只采用 2 个”不是本轮质量验收指标。

但来源 ID 碰撞是正确性缺陷，必须修复：

```text
source_id = "source_" + sha256(canonical_url)
```

发布前必须验证每个 `used_source_id` 都存在、标题/域名/URL 一致、一个 ID 只对应一个规范 URL。

### 8.2 必须使用 TDD

每项任务按以下顺序：

1. 先写能复现问题或表达目标契约的失败测试；
2. 运行并确认它因目标能力不存在而失败；
3. 实现最小完整能力；
4. 运行目标测试；
5. 运行相关回归测试；
6. 检查 diff 与工作树，不提交。

## 9. 实施时不得跨过的契约

### 9.1 薄 JSON＋完整 Markdown

- JSON 只负责路由、溯源、审核、搜索、待办和恢复。
- 卡片的完整内容必须保存在 `markdown`。
- 不为了让模型填复杂 JSON 而把报告拆成一大堆 blocks。

### 9.2 索引与 V1 闭包

- 每个可靠片段恰好被一个实质单元范围或一个明确排除范围覆盖。
- 每个索引单元至少被一张 V1 卡引用，或恰好进入 `omitted_units` 并说明不成卡原因。
- 索引未通过覆盖门禁时，不得启动第二次 V1 写作。
- 索引与逐字稿冲突时以逐字稿为准。

### 9.3 检查点和失败

- `beta8_event_index` 和 `beta8_all_scenes_v1` 分别持久化。
- 已有可复用索引时不重跑第一次；已有 V1 时两次都不重跑。
- 索引缺口最多允许一次带精确缺口范围的定向修复。
- V1 只有小范围 JSON/Schema 错误才可以修结构一次。
- 输出截断、网络中断或整体不完整时显式失败，不静默退回七次调用。
- 任何修复、重试或恢复都必须在计量中单独显示。

### 9.4 管线隔离

- 新管线值：`beta8_indexed_scene_v2`。
- `SingleReportRunner` 默认不变。
- 历史 `beta8_multi_scene_v1` 不自动迁移。
- 历史缺失 `pipeline_kind` 的数据继续按 `single_report_v1` 解析。
- 未知 `pipeline_kind` 失败关闭。

## 10. 最终验收标准

真实豆包逐字稿运行必须同时达到：

1. 正常 V1 阶段恰好两次调用；
2. 第一次覆盖 4 份豆包录音的所有实质内容，包括播客；
3. 每次真实工作沟通恰好对应一张卡；
4. 同沟通不按议题拆分，不同沟通不误合并；
5. 会议中讲述的第三方案例不被归成用户自身状态；
6. 无价值的简单日期卡不生成，但没有数量配额删除高价值卡；
7. 每张保留卡首屏有清楚核心信息，且内容足够丰富；
8. 呈现结构与内容类型匹配，不再大段堆叠；
9. 建议包含具体工具、模板、表格、话术、清单、步骤、实验或验证方法；
10. 正文先结论后论据，不使用第三方报告腔；
11. 不出现重复主标题和 `1 一、` 类重复编号；
12. Kimi 2.6 搜索决策不变，所有展示来源与引用正文一一对应；
13. 主体错误、工作沟通边界错误、未解决事实错误和搜索来源错配为 0；
14. 本次 run 单独提供总耗时、各阶段耗时、Token、费用、正常/修复/重试次数、Kimi 响应数、Web Search 调用数和终审分数；
15. 报告在原开发环境页面打开供用户直接检查。

最终人工判断必须同时满足：

- 保留 Y 的内容完整、核心判断清晰和小标题组织；
- 保留 X 的单卡丰富；
- 消除 X 的播客遗漏、缺少核心洞察和结构不稳定；
- 消除 Y 的内容单薄和帮助性不足。
