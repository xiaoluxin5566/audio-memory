# Beta 8 后续 Prompt 与运行协议 V1

**状态：** 待用户逐份审核的设计草案，不代表已经接入生产

**日期：** 2026-09-02

**适用对象：** Beta 8 七场景 V1 之后的审核、跨卡统筹、搜索与定向修改链路

## 1. 本目录解决什么

七个场景 Prompt 已分别读取完整可靠逐字稿，并在同一次调用中完成场景判断、价值判断和 V1 卡片生成。本目录只定义这些 V1 结果之后的处理，不重复定义七个场景的内容能力。

本版把“业务阶段数”和“必须维护的 Prompt 数量”分开，最终只维护三份核心 Prompt：

1. `01-unified-audit-prompt.md`：统一审核 Prompt，初审和终审复用；
2. `02-cross-card-orchestration-prompt.md`：跨卡统筹 Prompt，同时承担审核问题语义归并、卡片取舍、搜索规划和待办去重；
3. `04-targeted-revision-prompt.md`：定向修改 Prompt，只处理需要变化的卡片。

`03-search-execution-protocol.md` 是一个轻量搜索任务协议，其中包含给搜索模型或原生搜索服务使用的短指令。它不负责生成或评价报告，不作为第四份重型内容 Prompt。

## 2. 收敛后的调用链

```text
七个场景 V1 并行生成
        │
        ▼
统一审核 Prompt
├── 按逐字稿长度执行一个或多个 evidence_chunk 审核单元
└── 执行一个 global_report 审核单元
        │
        ▼
代码机械聚合
├── 校验所有审核单元是否完成
├── 合并结果但不擅自删除语义相近的问题
└── 为问题分配稳定内部 ID
        │
        ▼
跨卡统筹 Prompt（一次）
├── 归并语义重复或冲突的审核问题
├── 决定卡片保留、合并、删除、改归属或补生成
├── 形成逐卡修改任务
├── 汇总、去重并筛选搜索任务
└── 汇总、去重并核验待办候选
        │
        ▼
搜索执行
├── 代码做确定性去重、限额、缓存与重试
├── 搜索服务返回带来源的资料包
└── 搜索失败保留纯逐字稿路径
        │
        ▼
定向修改 Prompt
├── 只调用需要修改、合并或补生成的卡片
├── 未受影响 V1 字节级原样保留
└── 搜索资料只进入确实需要它的卡片
        │
        ▼
再次调用同一份统一审核 Prompt
        │
        ▼
全部审核单元无问题后原子发布
```

## 3. 为什么只保留这些 Prompt

### 不设置“审核合并 Prompt”

分段审核是为了解决输入长度，不是不同的审核业务。审核结果的完整性校验、拼接、精确重复去除和排序由代码完成。代码不得根据文字相似度删除问题；语义重复、冲突和跨卡影响统一交给跨卡统筹 Prompt 判断。

### 不设置独立“最终审核 Prompt”

初审与终审使用同一套事实、归属、推断、帮助质量和表达标准。运行时通过 `audit_phase=initial|final` 告诉模型当前是在发现 V1 问题，还是验证修改是否已经完成。终审不是降低标准的快速检查。

### 不设置重型“搜索报告 Prompt”

搜索阶段只执行已经批准的具体问题并返回带来源的外部资料包。它不能修改报告、判断录音内部事实或替用户作决定。真正如何使用资料，由定向修改 Prompt 完成。

## 4. 运行时最小对象

以下是语义契约，不是最终代码 Schema。正式实现时调用方提供 JSON Schema，Prompt 不硬编码完整 Schema。

### 场景 V1 卡片

- `card_id`：后端在场景结果校验后分配的稳定内部 ID；
- `scene_id`：七个正式场景之一；
- `markdown`：完整用户可见正文；
- `source_segment_ids`：覆盖关键事实、引语、判断和待办的逐字稿片段；
- `search_candidates`：场景提出但尚未执行的搜索问题；
- `todo_candidates`：场景内发现的真实待办候选。

### 审核单元

- `audit_phase`：`initial` 或 `final`；
- `audit_scope`：`evidence_chunk` 或 `global_report`；
- `audit_unit_id`：由后端分配，模型原样返回；
- `cards`：当前版本的全部候选卡片；
- `transcript_segments`：`evidence_chunk` 时提供当前完整分段，`global_report` 时可为空；
- `external_source_packets`：仅终审且卡片使用过外部资料时提供；
- `required_revision_tasks`：终审时提供，供检查任务是否完成。

### 审核问题

- `card_id`：问题对应的卡片；完全遗漏一张卡时为空；
- `issue_type`：事实、归属、推断、引语、遗漏、重复、场景边界、待办、外部来源、帮助质量或表达结构问题；
- `severity`：用于修改顺序，不决定是否可以忽略；
- `problem`：具体说明哪里有问题；
- `required_change`：说明必须怎样修正；
- `evidence_segment_ids`：支持该问题的真实逐字稿片段 ID；
- `affected_excerpt`：能定位问题时，复制最短必要的连续报告原文。

所有正式审核问题都必须修正，包括轻微问题。只要仍存在一个有效问题，终审就不能通过。

### 跨卡统筹结果

- `card_decisions`：逐卡保留、删除、合并、改归属或新建决定；
- `revision_tasks`：逐个最终卡片的完整修改任务；
- `search_tasks`：去重并筛选后的搜索任务；
- `todo_candidates`：去重并核验归属后的全局待办候选；
- `dropped_search_candidates`：未执行的候选及原因，供调试而不进入用户正文。
- `dropped_todo_candidates`：未保留的待办候选及原因，防止候选被无记录遗漏。

### 搜索资料包

- `search_task_id`：对应统筹结果中的搜索任务；
- `status`：`success`、`partial` 或 `failed`；
- `sources`：带 `source_id`、标题、URL、发布者、日期和可支持结论的来源；
- `answer`：只回答搜索问题，并明确哪些信息仍未验证；
- `error_summary`：失败或部分成功时的内部说明。

### 定向修改结果

- `card_id`：目标最终卡片 ID；
- `markdown`：修改后的完整用户可见正文；
- `source_segment_ids`：修改后仍被使用的逐字稿证据；
- `used_source_ids`：正文实际使用的外部来源；
- `todo_candidates`：修改后仍成立的待办候选。

## 5. 不可违反的运行约束

1. 七个场景的 V1 Prompt 是内容效果基线；本目录不能反向削弱其场景能力。
2. 每个审核分段必须是完整、连续且可核对的输入单元；后端负责证明所有单元均已完成。
3. 终审时，后端必须把每项修改要求分配给能够看到其证据的审核单元；全局结构要求交给 `global_report`。每项要求至少被一个适用单元检查，不能要求分段模型检查未提供的证据。
4. 审核聚合代码只能做确定性操作，不能把“文字相近”当作同一问题。
5. 跨卡统筹不直接重写正文，只输出决定和修改任务，避免一次调用同时承担总编辑和长文重写。
6. 未受影响卡片不调用修改模型，最终正文必须与对应 V1 完全一致。
7. 搜索资料不能证明逐字稿内部事实、用户或他人的动机、接受状态、决定、承诺、内部进度和真实待办。
8. 搜索失败、结果不足或来源不可用时，相关卡片回到纯逐字稿版本；不得用模型记忆补写具体外部事实。
9. 定向修改失败不能损坏已有 V1；终审失败不能部分发布；任何失败都保留最后一个有效版本。
10. 最终发布必须同时包含同一版本的卡片、全局待办、逐字稿证据关系和外部来源关系。

## 6. 当前不做的事情

- 不接入生产代码；
- 不替换现有 `backend/src/audio_memory/prompts/` 文件；
- 不改变七场景黄金 Prompt；
- 不决定具体模型、温度、Token 上限和并发数；
- 不执行真实联网搜索或付费模型调用；
- 不在 Prompt 中写死后端的完整 JSON Schema。

## 7. 审核顺序

建议按以下顺序由用户确认：

1. 统一审核 Prompt 是否真正覆盖内容真实性和帮助质量；
2. 跨卡统筹是否做了必要取舍但没有越权重写；
3. 搜索协议是否足以获得可引用、可追溯的资料；
4. 定向修改是否能完整修正问题并保留原稿中的强内容；
5. 四者串联后，是否能保护未受影响卡片并在搜索失败时稳定降级。
